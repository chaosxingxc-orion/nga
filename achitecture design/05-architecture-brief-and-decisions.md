## 1. 一页摘要

**agent-festival 在做什么**：给 openJiuwen（行内 agent 平台及其内核）加上「员工雇专家团干活」的机制。员工把业务任务交给超级智能体，超级智能体从目录里雇佣专家或专家团（多个专家加一张工作流）完成任务，责任在发起任务的员工。它不是新平台，是 openJiuwen 的增强。

**设计只回答三个问题**：

1. 专家怎么用机器能读的方式说清自己——**能力契约**；
2. 专家团怎么合成、怎么判权限、中间结果怎么共享——**执行图与授权衰减**、**三态时序协议**；
3. 每次采纳怎么追到人——**问责账本**。

**走到哪了**：三个问题的静态主线已经设计完并有机器形态（三份 JSON Schema 加双向一致性样例，检查器实跑全绿）；共享协议经两位架构师书面确认但机器形态为零；另外三块（上下文、动态主线、边界外主体）明确未设计。

**唯一的中心约束**：子任务拿到的权限永远是父任务权限的衰减子集；整体所需授权 ⊆ 发起员工持有的授权。

**最大的悬案**（第 7 节第 1 题）：授权的信任根要不要从「契约编译出令牌 + 吊销名单」迁移到「平台强制点注册表 + 证明测试 + 调用时快照交集 + 短期令牌」。这一题决定后续一半设计的走向。

## 2. 目标与边界

### 2.1 终局

架构师书面确认的终局（原话要点）：**全行一种超级智能体范式，是每个员工的统一入口**，业务任务由它雇专家或专家团完成。「一个」不是数量上的一个——企业内有智能体互联，对另一个智能体的委派走同一套判定与衰减。

金融业的智能体分**岗位智能体**与**面客智能体**两类，这一句仍待书面确认（它们是两个信任边界，不是两个功能）。

### 2.2 由终局反推的六条前提

1. **专家不是智能体，是能力**——无身份、无跨调用记忆；
2. **专家团不是组织，是围绕一个任务的多个专家加工作流**；
3. **岗位不是智能体，是授权范围加知识上下文**；
4. **任务树与授权衰减树是同一棵树**；
5. **两类超级智能体是两个信任边界**，不是两个功能；
6. **一个智能体必须在内部消化职责分离**——同身份、独立上下文的验证者。

### 2.3 不做什么

- 不做承载智能体的云，不卖算力和沙箱；
- 不造通信协议（用 A2A：Agent-to-Agent 协议，Linux 基金会项目）；不造注册中心（站 AGNTCY 与 Nacos 生态）；
- 不做异构智能体互联平台——企业内互联只是委派的一种；
- 实现语言未定（Java / Python / TypeScript 待选，这是待裁项之一）；现有 Python 脚本只是规格检查器，可抛弃。

## 4. 已设计的部分，与为什么这么设计

### 4.1 领域模型：什么概念才配有名词

**准入规则**：一个概念只有需要独立的契约字段分化、或构成独立信任边界，才获得自己的名词。

八个领域概念：**Agent**（持签名身份，信任边界）、**Task**（业务任务，预算衰减的单位）、**Skill**（= 专家：无身份无记忆的能力包）、**Tool**（最大爆炸半径来源）、**Resource**、**Role**（授权范围，不是身份）、**User**（员工：责任主体，在智能体系统之外）、**Contract**。三个运行时概念：Session、Policy、Hook。

「专家团」「分身」「团长」这些口语**不立名词**——它们是执行图的读法，不是新概念。

**为什么**：早期「本体」撞名 Palantir Ontology；每个新名词都会变成 schema 字段与维护负担。准入规则让「选词」变成可判定的操作。

### 4.2 三面视角与四条不变量

**管理面、控制面、数据面不是三套系统**，而是同一份声明式文档（契约、执行图记录、策略）和同一条账本在三个时刻的投影：

| 面 | 时刻 | 谁在动 | 干什么 | 持有真源 |
|---|---|---|---|---|
| 管理面 | 编写，天级 | 人（技能作者、目录管理员、合规官、审批人） | 目录、发布与认证、策略编写、审计查询、审批台 | 三份：目录、策略、账本 |
| 控制面 | 准入时整体判定一次；每节点调度时签发一次 | 确定性代码 | 合成与判定、令牌签发与吊销、预算切分、验证门 | 无自有真源：读管理面，写账本 |
| 数据面 | 每次工具调用 | 模型循环加 Hook | 持令牌执行、经强制点验令牌、发事件 | 无真源，只有执行状态 |

**四条不变量与理由**：

1. **确定性住在控制面**——策略判定不由模型做，模型只作审阅建议者，门是代码加人。理由：审计要求判定可复现。业界四个框架的模型审批都是可选项且排在确定性拒绝之后；本设计比它们更严，判定完全不经模型。
2. **数据面不能写真源**——智能体进程不能改目录与策略，账本只能追加。业界站台：hermes 禁止智能体写配置；claude-sdk 里智能体提议的规则落不进 policySettings 的策略三层；openclaw 自更新「绝不由模型发起」。
3. **任务钉在准入时刻的目录与策略版本上**——准入后策略收紧靠吊销生效，不可逆动作执行前联机核验。令牌里带目录版本哈希，账本能重建「当时按哪一版判的」。**诚实说明**：版本钉住在凭据与身份界是刻意留白的（Vault 策略实时解析、Kubernetes RBAC 按名称引用，都为热更新牺牲了可归因性）；先例只有 Argo CD 的 targetRevision、Temporal 的 worker 版本化、SpiceDB 的快照令牌三型。这是本设计的自选约束，需要自证价值。
4. **强制点分两层**——进程内 Hook 拦每次工具调用；不可逆动作在资源侧再验一次令牌与参数范围。理由：Hook 与模型同进程，被攻陷的进程可以绕过它，所以只靠 Hook 守的必须是可逆动作。业界站台：openclaw「可信网关、不可信执行」。

**管理面是控制面的高阶自应用**：发布一份契约、升级一版策略，本身就是一次 Task，走同一判定与同一条账本。样例已验证：目录管理员发布契约必须通过；评估流水线没有目录写权，同一动作必须拒绝。先例：Kubernetes Cluster API 用同一套声明式 API 管理集群的生命周期。

**为什么这么设计**：三套系统会出现三份真源、三种漂移；声明式单真源 + 时刻投影让「当时按什么判的」永远可查——这是问责的根基。

### 4.3 能力契约：四段

契约是专家的机器可读自述，四段：

- **provides**：能做什么（含输入输出合同）；
- **requires**：要什么授权——权限是「资源（data / tool / network / agent / secret 五类）× 动作（read / write / execute / delegate）× 副作用（none / reversible / irreversible 三档）」的矩阵；
- **effects**：改变什么（副作用等级、补偿动作）；
- **bounds**：预算上限（调用次数、成本、时长——并行时签发切分）。

两条硬规则及理由：

1. **强制不了的不许进 requires 的机器判定栏**——机器判定不了的（比如「这个工具承诺不外发」）进评审判定栏，由人审。理由：把不可强制的声明放进机器栏是假承重，出事时账本显示「已授权」反而误导问责。
2. **选择器任何环节不解码**——资源选择器只收可打印 ASCII 与规范百分号编码，编码形态对编码形态匹配。理由：解码形态的形近字符（全角星号、零宽字符）枚举不完，是安全匹配的经典绕过面。

**签名与信任**：契约是独立签名文档，信封逐字复用 A2A 的 AgentCardSignature 三字段，载荷按 RFC 8785（JSON 规范化）处理；多签必须全部通过（坏一条是篡改信号，不是噪声）；**签名人与主体绑定**——可信密钥库里每把密钥只能为列名的主体签，未绑定密钥算背书方。

**为什么独立文档而不是塞进名片**：名片签名只能表达自声明；独立文档让多背书方（技能作者、目录管理员、认证方）各自签名、各自担责。

### 4.4 执行图与授权衰减

**专家团的机器形态是一份执行图文档**：`nodes`（各专家的契约）、`edges`（结论供给关系）、`plan`（顺序与并行）。

**合成规则**（图 → 一份合成契约）：授权取并集、副作用取最严、预算按串行求和与并行取最大。

**判定只有一句话**：整体契约需要的授权 ⊆ 发起员工持有的授权集，且副作用等级覆盖。「员工持有的授权集」来自行内身份与权限系统，本设计不另造。

**四条设计决定与理由**：

1. **衰减是硬约束**（子任务权限 ⊆ 父任务）。业界在这点上是分裂的（hermes、codex 强制；AgentScope、LangGraph 不强制；zcode 按来源防提权）。本设计自选强制，理由：银行要可证明的最小权限；架构师的问责模型「员工雇团、责任在员工」只在团做不了员工做不了的事时才说得通。业界没有「逐任务合成签发」的先例，这是本设计的独有面。
2. **预算在签发时切分**，不用共享计数器。理由：共享计数器是经典的检查-使用-时间差竞态；签发时切分让子任务超预算被自己的令牌拒绝，没有可竞争状态。业界没有按任务图切分预算的先例（预算都挂在静态主体上）。
3. **「上游供给」是被校验的声明，不是对所需授权的减法**。早期「减上游供给」是概念幻觉（对并集恒为空操作）；现在的语义是：本节点令牌不含此项、供给方须持有同等授权，沿边按调度顺序校验。
4. **并行预算在签发时切分**（0.1.0 为均分）；可切分的量（token、成本、墙钟、重试）切给子任务，不可切分的量（同时存活数、累计派生数）由控制面集中计数。

**治理即任务**（见 4.2 末段）已有双向样例验证。

### 4.5 目录与规约翻译（与邻居资产的关系）

邻居三仓（bitlhk 团队的 EA / FSE / FAH）充当**规约层**，本设计不造第四套包格式：

- EA 的岗位包是 Agent / 岗位规约；GRACE（EA 的受治理上下文解析规范：任务声明需要哪些知识与数据、组织把逻辑资产绑定到物理源、解析出带溯源的上下文条目）是上下文规约；
- FSE 的 Skill 规范是 Skill 规约；其产物封套（资产摘要 + 上游摘要 + 级联失效 + 弃权一等 + 人工关口不可替代）是认证凭证换版失效的现成形态；
- FAH 的业务组件包是能力件规约，其「声明源码与实际加载制品分开记摘要」是认证凭证钉住实际制品的直接范本。

**规约翻译层**（2026-10 完成映射表）：三套包格式都能编译出契约四段的骨架，但**没有任何一套自带完整四段**——provides 三家都有载体；requires 各有成熟局部；effects 靠枚举映射收敛（八值 / 三值 / 二值收敛到三档，只许收紧）；**bounds 四处全无，必须由发布流水线的治理动作注入**，空预算即拒绝发布。

**为什么**：银行环境的技能来源会是多套规约并存；腰身最窄（契约 + 执行图 + 签名三样）让接进来的包格式不需要为兼容本设计增加专属字段。

### 4.6 三态时序协议（中间结果的共享范围）

每个专家的中间结果经历三个状态：**草稿**（只有自己可读写）→ 写入结论槽位即**封存**（之后不可再写）→ 消费方被签发令牌时**揭示**（下游此时才读得到）。

- 载体是两个命名空间：私有草稿 `task://{task}/context/<节点>` 与结论槽位 `task://{task}/conclusions/<节点>`（工作池是并行组声明的第三形态：组内开放、组外沿边、出组封存、只追加）；
- **授权由图派生，不由契约作者手写**：合成器为每个节点派生自己草稿与槽位的读写权、为每条边派生「读上游结论」；手写 `task://` 一律拒绝。**默认即隔离**——没有边就读不到任何别人的东西，要多共享就加边或声明工作池；
- 协同 / 对抗不是字段，是同一协议的不同排法（流水线、并行互审、对抗辩论、工作池协同）；关系类型是从图算出的读出值，不存储。

**为什么**：多个专家的价值来自误差相互独立；提交前共享中间结果会把独立性毁掉。三态原语把「对抗要控制共享、协同要共享复查」统一成一个时序规则，而不是两套机制。

**诚实说明**：协议经两位架构师书面确认，但机器形态为零（`task://` 文法、派生函数、封存的运行时强制都未实现）；已知没关上的口子有两个——对抗方共享检索源的侧信道（缓解：评审期计算重叠度、共享上游只授只读）与宿主自带的智能体间直接消息（对抗排法下必须关掉）。

### 4.7 问责账本

三个锚点：

1. **谁做的**永远记持签名身份的 Agent（归因锚）；**谁负责**是经 Session 解析到的 User（员工）。Skill 两者都不是。
2. **采纳是一等事件**：`adoption{专家, 会话, 岗位, 结果 ∈ 采纳 / 修改后采纳 / 拒绝 / 裁决, 依据}`——把架构师指出的「采纳不透明」做成可查记录。
3. 对任务上下文的每次读写带（会话，专家，岗位）三元组。

**为什么**：归因与责任是两件事（做了 vs 担责）；把它们分开，将来责任上移到智能体或法人时只改账本查询视图，领域模型不动。

### 4.8 机器形态与业界关系的现状

- 三份 JSON Schema 0.1.0（契约、签名信封、执行图）+ 双向一致性样例（必须通过 5+15 / 2+16 / 3 / 4 / 8+28），检查器 2026-10-28 实跑全绿。样例是任何实现的一致性测试向量。
- **治理语义层是业界独有面**：任意深度的「所需 ⊆ 持有」判定、写一次即封存的结论槽位、采纳一等事件、问责三锚点、对侧信道的显式承认——九个开源框架与约五十个管理面 / 控制面候选（2026-10 调研）里均无先例。
- **诚实说明**：本设计标「未开始」的底层机制，业界多半有现成形态可借——短期令牌（Vault / OpenBao 的租约与即时吊销）、每单元短期令牌（Kubernetes TokenRequest）、存量执行钉版本（Temporal worker 版本化）、工作负载身份（SPIFFE / SPIRE：为服务签发短期加密身份的规范与实现，但「非为 agent 设计」的批评成立）、企业集中管理智能体会话授权的规范（MCP（Model Context Protocol，模型上下文协议）社区 2026 年定稿的 Enterprise-Managed Authorization，与本设计控制面同构）、数据面强制点与网关控制面（agentgateway，Linux 基金会项目，工具级 scoping + 预算事前截断 + 防篡改审计）。**借件清单齐全，整体机制零先例**——这正是本设计的位置。
- 大厂模式一致：治理四件（准入判定、凭据签发、租户权限、审计账本）全部沉淀在闭源云服务（AWS AgentCore 是最完整对偶物）；开源世界没有一家覆盖本设计的管理面 + 控制面整体。

## 5. 明确未设计的部分（诚实清单）

## 7. 需要你裁决的九个问题

每题给出：问题、为什么需要裁、本设计的默认与理由、不回答的后果。逐题批复「同意默认」或给替代意见即可。

### 第 1 题（最重）：授权的信任根放哪

**问题**：任务授权的最终依据，是「发布方契约编译出令牌 + 吊销名单」，还是「平台强制点注册表 + 属性级证明测试 + 调用时快照交集 + 每次调用的短期资源侧令牌」？

**为什么难**：bitlhk 三仓（同属一个生态）用后一种范式做成了能跑的系统（强制点注册表、逐调用快照交集、短期令牌），且与我们纸面上写的一致；但审查发现其「证明测试只证明拒绝路径存在，不证明每个声明的属性被消费」——注册表也是声明，声明同样会「声明了没接上」。两个范式各对一半。

**本设计的默认**：**嫁接**——契约四段降为**准入证据与注册表的来源**（由合成器编译成平台强制点注册表条目，每条带属性级证明测试）；执行图保留编排与共享范围职责；每次资源侧调用签短期令牌。

**附材料**：若控制面选用判定引擎组件，存在选型分水岭——关系模型系（OpenFGA、SpiceDB）无原生决策日志，策略语言系（OPA、Cerbos）有；判定侧与账本侧要不要同源影响选型范围。

**不回答的后果**：令牌、吊销、版本哈希整体无法定稿；已落地的信封与签名体系中哪些被新信任根取代、哪些保留，无法写明。

### 第 2 题：令牌与新鲜度路线

**问题**：吊销与新鲜度靠长效令牌 + 吊销名单，还是短期令牌 + 调用时快照交集？

**默认**：不做长效令牌与吊销名单；每次资源侧调用签不超过 120 秒的令牌；调用时裁决 = 任务快照 ∩ 当前快照 ∩ 当前操作，快照必须含资产授权集与目录版本指纹（业界现成方案缺这两样，撤资产授权感知不到）；一次性消费去重集中存储。

**附材料**：MCP 社区 2026 年定稿的 Enterprise-Managed Authorization（企业身份系统集中签发与管理 agent 会话授权）与本设计控制面同构，另有 AuthZEN 授权查询标准；本路线应与这组规范对表。

**不回答的后果**：动态主线（第 5 节第二大缺口）整体无法设计。

### 第 3 题：执行图 0.2.0 的三种控制结构

**问题**：执行图要不要承载分支与循环？到什么程度？

**默认**：三种——① 受限表达式的条件（白名单函数、无副作用、准入时可静态分析）；② 图上声明的有界循环（轮数、重试、墙钟三维小上限）；③ 新增「包络节点」承载运行期派生：准入时批准深度、同时存活数、累计派生数、可切分预算、工具并集；之后每次派生检查「新增 ⊆ 剩余包络」，检查挂所有派生入口的公共汇合点，准入后只许收紧。

**理由**：业界真正的分界线是「图在准入时是否确定」（只有 LangGraph 与 openJiuwen 编译后冻结）；循环封顶业界全是计数器，分「防失控大数」与「有意义小上限」，本设计要后者且写在图上——让循环留在准入看得见的地方，不是「循环已被证实为刚需」。

**不回答的后果**：执行图 0.2.0 没有启动条件；循环要么禁（表达力不足）要么放任（预算与权限失控）。

### 第 4 题：工具包构建期的两条新条件

**问题**：闭环构建（builder 在构建期执行被装配方代码，可能用测试域真实凭据对外发调用）带来构建期风险，要不要补接入条件？

**默认**：补两条——**构建 / 认证流水线执行产物代码必须在与其自身凭据、网络隔离的子进程进行，环境白名单**；**闭环构建运行本身是一次治理 Task**（替代方案是另开治理轨道，不倾向：治理动作统一为 Task 已有先例与样例）。

**不回答的后果**：接入条件只覆盖产物、不覆盖构建过程；「认证的是 A、发布的是改写过的 A′」这类缺口在构建期重现。

### 第 5 题：员工个人智能体的平级协作（对等联邦）

**问题**：两名员工各自的个人智能体平级协作（B 的智能体凭 B 的身份行事、B 同意），「委派 = 子 ⊆ 父」表达不了，要不要开放？

**默认**：暂不开放。现有委派模型覆盖当前阶段；对等联邦留待第二信任边界（面客侧）一并设计。

**不回答的后果**：无直接阻塞；但「企业内互联」的语义边界（委派 vs 平级）长期含混，影响目录与账本的主体模型。

### 第 6 题：系统边界外的主体（四小题）

**默认**：监管强制事件（不由员工发起）建模为「平台域 User」发起的强制 Task，走同一判定与账本（「User 是所有 Task 的根」不破，加的是一种 User）；客户适当性 = 面客智能体侧的前置校验 Task，结论入账本；员工外部执业资格 = 岗位包的准入条件（认证凭证附件）；平级协作见第 5 题。

**不回答的后果**：三类主体的责任锚悬空——账本答不了「监管抽查这笔谁负责」「给客户的建议谁担责」。

### 第 7 题：契约编译目标的范围

**问题**：契约编译到宿主原生权限格式，先只做自家运行时，还是扩到外部宿主？

**默认**：先自家，两个目标——场景级 actrule（DeepAnalyze 的权限规则文件格式）与团队蓝图（DeepAnalyze 的编排定义），两者都是「契约 → 权限 → 强制」的现成通道、已代码级验证。外部宿主（如 agentgateway）等「宿主接入条件」成型再扩。

**为什么有前提**：每个宿主都有放宽通道（实测七类：模型直接放行替代人批、「总是允许」仍生效、委派例外、空清单即继承全部、沙箱静默降级、强制只挂部分路径、宿主自带智能体间消息）；接入条件须逐条声明并配开关，**准入时把实际生效的策略读回来核对，不一致即拒绝启动**。

**不回答的后果**：编译通道范围不明；已勘明的外部宿主对接要么无法推进要么贸然推进。

### 第 8 题：S0 原型岗位

**问题**：第一个原型场景选哪个？

**候选**：**财富经理**（三仓规约唯一全覆盖：EA 岗位包 + 评测、FSE 目录与评测包、FAH 财富只读切片 + 真实 Java 运行时）；**贷后风控**（次选，三仓也都有）；**DeepAnalyze 场景**（2026-10 新增候选：最接近的已跑通宿主，权限管线与团队蓝图现成）。

**不回答的后果**：S0 无法启动，连带实现语言的决定也缺场景输入。

### 第 9 题：实现语言

**问题**：Java / Python / TypeScript？

**现实输入**：治理平台 TS（EA）、金融能力底座 Java 并接 openJiuwen Java（FAH）、运行时 Python；DeepAnalyze 与 openJiuwen 内核是 Java；Spring AI Alibaba Admin（Java 管理台）是 2026-10 新输入。多语言是行业现实，治理层与运行时分语言已有先例。

**不回答的后果**：任何实现代码不能动（这是本设计的自设门禁）。

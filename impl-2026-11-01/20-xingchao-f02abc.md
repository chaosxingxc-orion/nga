# F-02 补充与修正：固定业务流程、节点执行幂等、知识消费快路径

这是项目负责人对上一轮 F-02 的进一步明确，补充 Issue #1 评论 197992606，并**修正其中可能被理解为“生产运行时由 S2 持续重规划业务链路”的表述**。本轮将 F-02 拆为 F-02A、F-02B、F-02C，请以本回复作为该项最新的我方反馈。其余 F-01、F-03 至 F-06 的企业治理、知识工程、语义规约保鲜、开放原语和 openJiuwen 复用方向保持有效。

这里有三个不同的问题：规划如何避免不确定性、执行节点如何保证结果与效果幂等、如何通过知识消费减少模型计算。不能因为决策幂等已经对齐，就认为另外两项自然成立。

## F-02A｜业务流程在开发态配置，发布后固定，生产运行不逐次重新规划

### 为什么

相同上下文交给 Agentic Model，可能生成不同工作链路。即便最后答案相同，取证过程、工具调用、成本和外部效果也可能不同。在企业生产业务中，没有必要每次重新发现“这项业务应该怎样执行”。

项目负责人的明确要求是：业务执行依照已确认流程；开发过程可以参考智能体开发方式，由模型辅助形成候选配置，最终输出是 Loop Forest 中的一张图。图确认并发布后，该版本固定，业务按流程最大化保证稳定性和幂等。

### 明确采用什么原则

| 阶段 | 允许的工作 | 输出及边界 |
| --- | --- | --- |
| 开发态 | 人与 S2 辅助理解业务、配置节点、设计与验证候选图 | 尚未生效的流程候选 |
| 发布阶段 | 按管理面规则确认流程、节点契约和依赖 | 不可变的已发布版本 |
| 运行态 | 在已发布图内处理任务，S1 判断业务分支，节点完成工作 | 不重新生成或替换该任务的业务流程图 |
| 运营与进化 | 分析问题、提出新流程或节点配置 | 进入后续版本验证与发布，不回写正在运行的历史图 |

固定图可以包含条件分支、循环、补证、等待及异常出口。S1 根据语义规约、证据和任务状态，在这些已定义路径间进行决策式跳转。**选择预定义分支不等于重新规划流程。**

图覆盖不了的情况，应进入规定的异常处理，如暂停、人工处置或形成改进案例。S2 可以建议修改图，但不能在生产执行中自行将建议变成当前业务流程。

### 如何落地

任务绑定已发布图、节点配置及必要依赖。框架记录每次节点进入、分支判断和推进依据。开发态可使用 S2 规划能力；运行态的 S2 只在节点契约允许的范围内完成工作、消费知识和反馈问题。

局部执行方法是否允许调整，由节点契约和管理规则明确，不能用“节点内重规划”重新打开任意改变业务顺序、证据要求或外部效果的通道。

因此原先的主线应修正为：

> 开发态配置并发布业务图 → 运行态 S1 选择已定义业务路径 → 节点中的 Agent Loop 完成限定任务 → 结果与异常形成运营反馈 → 必要时产生新版本候选。

**价值与限制：** 固定图消除了逐次生成业务流程的不确定性，但仅固定图不能证明节点输出或外部效果幂等，后者由 F-02B 单独保证。

## F-02B｜节点采用 Agent Loop 式执行接口，但幂等由执行契约与框架机制保障

### 为什么

每个执行节点内部运行 Agent Loop 式智能体后，生成式模型的不确定性仍可能存在。不能要求模型靠记忆“上一次说了什么”，也不能只给它一个“请保持幂等”的提示。

需要先区分两种保证：

| 保证 | 所指问题 | 主要机制 |
| --- | --- | --- |
| 同一次节点工作重复调用 | 重试、恢复、重复消息应取得原工作结果 | 稳定执行身份、持久记录、结果复用与重复处理 |
| 两次独立工作依据语义等价 | 重新执行也应保持业务结果一致 | 明确语义规约、有效数据依据、确定性处理或合格的 S1 判断与验证 |

缓存第一次结果解决第一类问题，但不证明第一次结果正确，也不证明第二类语义一致性。相同文本输入不自动等于同一次业务请求。

### 节点执行协议应具备什么

1. **确定执行身份。** 关联任务、图版本、节点和本次节点执行实例。循环中合法的下一次进入可能是新工作；重试上一次进入仍是原工作。具体字段可以复用已有能力，不预设新的身份系统。
2. **绑定实际消费依据。** 包括实质输入、语义规约、证据/数据快照、必要参考时间和依赖版本。依据应可追溯，不能仅按提示词文本匹配。
3. **先查执行记录。** 已完成则返回已提交结果；执行中则关联原执行；正在等业务响应则继续原等待；同一执行身份携带不同实质内容则按契约处理冲突。
4. **没有可复用结果再执行。** 优先尝试 F-02C 的知识消费快路径，需要时才驱动模型循环。
5. **验证候选结果并提交。** Agent Loop 输出先是候选；依据节点契约验证后，由框架提交正式结果及依据。重复完成或迟到候选不能覆盖已提交结果，修订应有明确规则与关联记录。

“框架”在这里指需要满足的控制语义，不要求再造独立执行主控；请优先映射到 openJiuwen 已有执行、状态和恢复能力。

### 节点结果幂等必须覆盖内部业务调用

只在 Agent Loop 最外层保存结果不够。例如：节点已提交授信请求，但还未保存节点完成结果就中断；如果恢复时重跑整个 Loop，可能再次发出业务请求。

因此节点内部每个有业务效果的调用也需要：

- 绑定原业务请求及实质载荷；
- 按提供方能力实施幂等提交、查询、等待和受支持的恢复；
- 默认等待 API 的实际响应，区分受理与最终结果；
- 重试、换工具调用编号或局部策略调整不能创建新的业务意图来绕过原请求；
- 提供方不能保证的部分明确保留，不能用本地缓存宣称外部效果已幂等。

这不要求 NGA 操作银行内部数据字段，也不要求重建银行事务逻辑；业务 API 内部的规则和最终效果仍由原系统负责。

### 正式结果应是什么

节点应有稳定的业务输出契约，区分正式业务字段、证据、状态与解释文本。例如“历史逾期核验”节点可以交付：证据覆盖范围、是否存在符合否决条件的记录、引用记录、消费的语义规约版本、是否满足证据要求。

可确定性完成的部分使用确定性能力；需要语义判断的部分交给合格的 S1。S2 可以调查、整理与调用工具，但自由生成的一段解释不能自动成为正式业务事实。

如果某个输出完全由自由生成的 Loop 决定，又没有稳定依据和判定机制，就不能承诺独立执行时一致。结果验证也不能仅验证字段齐全而宣称证明了业务正确性。

如正式交付文本要求逐字一致，应保存并复用该交付版本；展示性解释不能反向改写正式业务字段。

## F-02C｜Agent Loop 应有知识消费快路径：以存代算、以存助算

### 为什么

同类工作反复调用模型重新搜索、推理和生成，既浪费计算，也重复引入不确定性。已确认的结果、经过验证的方法和有效知识应成为正常执行入口，不应仅作为可选提示词附件。

节点采用 Agent Loop 式统一接口，不意味着每次都必须调用模型。一次执行可以直接复用正式结果，也可以执行知识化流程，必要时才展开生成式循环。

### 三类知识消费必须区分

| 命中对象 | 使用方式 | 适用边界 |
| --- | --- | --- |
| 同一次执行已提交的结果/回执 | 直接返回，不调用模型 | 身份与绑定内容一致，调用者有读取权限 |
| 经验证的规则、Workflow、计算或工具使用方法 | 按已定义步骤执行，省去模型规划与部分推理 | 输入条件、版本、授权及适用范围匹配 |
| 历史案例、经验与记忆 | 辅助当前调查、执行和判断，减少搜索 | 有来源与有效性，不能自动升级为当前事实或正式结果 |

授信例子：

- 同一次申请的业务回执已经确认：复用原回执。
- 已知如何从合格数据源获取历史记录：直接运行已发布查询流程，无需模型重新设计调用方法。
- 相似客户曾经获批：可以作为适用范围内的参考，不能把另一客户的批准或另一独立请求的回执复制过来。

**命中不只意味着文本相似。** 语义检索可以发现候选知识，但直接复用需要满足明确的业务适用条件。新的独立业务请求即使复用了计算方法或判断知识，也仍有自己的请求身份与效果记录。

### 保鲜与控制如何保留

快路径要消费 F-04 定义的语义规约有效性、依赖与保鲜信息：

- 历史正式结果作为原请求事实保留，不因新规则而静默改写；
- 知识、规则与方法用于新任务时检查当前适用性；
- 失效或被替代的资产可以解释历史，不自动用于新的生产判断；
- 复用不绕过当前授权、节点完成条件和必要审计。

“以存代算”复用已经确认的结果或可执行方法；“以存助算”用有效知识帮助完成新工作。存储形态可以是记忆、知识库、规则库、案例库或其他合适组织，不在本轮锁定技术产品。

## 三项机制合起来的节点运行主线

> 进入已发布图的节点 → 绑定执行身份与依据 → 查询原执行状态 → 已完成则复用、未完成则继续 → 无原执行结果时匹配有效知识快路径 → 必要时调用模型循环 → 验证并提交正式结果 → 按固定图继续；业务语义分支由 S1 判断。

这里有两种不同的回路：**运行中的局部 Agent Loop**完成固定节点的任务；**运营到开发的改进回路**产生新图或新配置版本。两者不能混成“运行智能体随时重写业务流程”。

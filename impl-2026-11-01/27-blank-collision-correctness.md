## 〇、总裁决

**对方新议题「幂等≠正确」＝对我方架构一个真实空白的正确命名，且打击点准确。** 它既不是全新发明（我们自己三个战场已把同类机制交付过三次：EDPA DeterministicChecker、LoopForest VetoRail、hermes 式质量门——最后一个在 frame-bench），也不是过度要求（对方自己明确拒绝「框架保证所有业务判断 100% 正确」的承诺，198232012:43）。它是我方「T0 验证控制语义 / T1 验证模型能力」分工宣言（e2e doc.go:14-18）自然推导出的**第三块拼图**：框架对判断正确性的保证面。我们宣布了前两块的存在，却从未声明第三块的归属——对方现在要求我们补上这张地图。

**采纳形态（总裁决）**：
1. **反例 A（稳定错误）**：认领为架构级真实缺口。采纳「规格驱动的确定性校验」——判断规格是唯一真源，双消费：S1 的 prompt 与确定性校验器共读同一规格版本（EDPA「规则 > LLM judge」形态移植），校验位在采纳边界、结果进 adoption 载荷与 digest。机器保持语义不透明（其章程），校验是图级独立节点。
2. **反例 B（证据缺失）**：认领为半缺口——夏裁决的差集告警（DECLARED-vs-QUERIED）已有，但对方要的是另一个差集：REQUIRED-vs-AVAILABLE（判断规格声明必需证据覆盖，快照对账）。两者是不同的差、不同的机器判据。
3. **反例 C（错误复用）**：认领但重定位——主体在已采纳的场景 R/K 里程碑上，新增一个概念：「当前有效性」是投影不是改写（增量修订+关联状态查询），与我方 T0 场景 3「历史不可改+双修订独立可归因」的既有形态同构。
4. **五层拆分**：接受拆分、拒绝「层」的隐喻——它们是五个正交验证主体（各自有方法/所有者），不是栈。补两行缺行（见 §六）。
5. **关键保留（对方论证的一个真实漏洞）**：反例 A 的「独立校验」的**独立性取决于事实来源的独立性，不只是校验器的确定性**。校验器若消费 S1 自己提取的事实，它验证的是规则应用、继承的是提取错误——对方的测试设计（注入总错的 S1、喂预结构化事实）会制造虚假安全感。生产形态中「4 个月逾期」这个事实是某语义过程从原始材料里提取出来的，那一半才是 Jev 的合法领地。

**一句话**：对方说「能检查的约束必须检查」——我们答应；我们回敬一条他们没写的判据——**独立校验的独立性边界＝事实提取边界**，这条边界外的保证必须按他们的四句要求（受控处理/可发现/可纠正/防传播）治理，而边界内的保证是机械的、可 100% 验收的。

## 一、对方新议题的本质：新问题，还是已有架构的自然延伸？

**判定：既非纯新问题，也非纯延伸——是我方设计哲学的一个已声明空白，被对方正确命名。**

### 1.1 我方现状的诚实解剖

我方架构对判断的处理链是（e2e_test.go:200-257 happy path）：

```
S1 判断（s1Judge，规则内嵌于 stand-in）→ 机器采纳（Adopt）→ 派发（Dispatch+14-A4 复检）→ 业务 API → 终态
```

机器的章程写得很清楚（e2e_test.go:276-278）：

> "The machine does not interpret business semantics — the verdict lives in the payload, opaque to the gate"

即：**采纳闸对判决语义完全不透明**。T0 的 s1Judge 是确定性 stand-in、内嵌修正后的规则（e2e_test.go:48-65）——它同时扮演了「规则载体」和「判断者」两个角色，而**没有任何组件独立校验它的输出**。T1 把规则写成 prompt 喂给真 LLM 并预注册硬杆（t1_llm_test.go:80-116，C2 是「the load-bearing discrimination case」），run-1 7/7——但那是**模型能力测量**，不是框架保证。若在 T0 注入「永远 grant 且高置信」的 S1（对方 198232012:114 点名要求的测试），当前机器会顺利 adopt+dispatch——**反例 A 在我方当前架构中是活的洞**。

我方此前的诚实边界声明（e2e doc.go:14-18）「model stand-in validates the framework, not the model; the model-capability tier is separate and real-LLM」——这个分工本身没错，错在**没有第三个格子**：框架对「判断正确性」的保证既不在 T0（控制语义）也不在 T1（模型能力），而是无人认领。对方问的就是这张地图上缺的那格：谁来保证、怎么保证、保证到什么边界。

### 1.2 五块既有资产已经为第三格提供了插座

- **判断规格（judgment.schema.json）已经是机器可消费的**：rules 有 precedence/coverage/exceptions（:140-171），examples 有 boundary/equivalent/competing/unresolved 四型反例（:192-224）——一份可执行确定性校验器所需的全部结构都在，但 examples 目前只是声明性文档，**从未被执行为探针**。
- **采纳闸有现成插槽**：Adopt 与 Dispatch 之间已经站着一个独立复检（14-A4 权限复检，adopt.go:337-360）——同一个插槽形态可以容纳规则复检（载荷内新增校验维度）。
- **版本钉照已经存在**：versions 有 rule/model/readout/policy 五维（adopt.go:74）——校验器与 S1 消费同一规格版本可被钉死，防止「校验器用的规则和 S1 用的规则不是一个版本」的分叉。
- **evidlog 差集告警**（夏 round-1）是 B 的半边插座。
- **修订身份已经分立**：identity 有 BusinessRequestID + EvaluationRevision（adopt.go:163）——C 的关联修订有身份基础。

**结论**：对方议题的正确形态不是「另起正确性引擎」（他们自己也说「不要求一开始建一个新的通用正确性引擎」，198232012:84），而是把已有插座的空白插槽填上。4-lens 里的 Simplicity 判据在此裁定：新增一个「通用正确性引擎」是雕花；在 adoption 边界加一个规格驱动的确定性校验节点是补缺。

## 二、三个反例逐个分析

### 2.1 反例 A：证据在，S1 稳定判错

**对方设定**（198232012:109-114）：资产 3500 万、近 6 个月无逾期、可信材料记录两年前 4 个月逾期，S1 输出 grant。「历史任意一次超 3 个月即否决」已发布且事实为可核验结构化输入→领域规则/验证方法应能发现冲突，框架不得因 S1 稳定或高置信就派发；并要求故意注入「每次都错且高置信」的 S1 做故障注入验收。

**我方判定：全击中，认领为架构级缺口。**

- 机器层事实：Adopt 只查请求文档 schema 合法性（adopt.go:267-269）、不查判决内容；Dispatch 只复检 grants（:356-359）；判决对闸不透明（e2e_test.go:276-278）。**当前没有任何东西能拦 A。**
- 能拦 A 的形态（三资产同型）：
  1. **EDPA GroundTruthVerifier + DeterministicChecker**（edpa wiki :219-237）：criterion 先匹配确定性 checker（`matches`），命中则纯计算（`check`，零 LLM），不命中才 keyword 兜底——铁律「规则 > LLM judge」就是为 A 这类「数值/逻辑/合规判断交给 LLM-as-judge 不可靠」立的法。credit 场景的 veto 是典型 formalizable 约束：`any(o.months > 3 for o in overdueOnRecord) → deny` 是纯谓词。
  2. **VetoRail**（VetoRail.java:22-40）：写入契约 veto 拦截 LLM 输出，双模型实验 bait 执行率 50%→0%、SAT 不伤——「确定性拦截层拦住 LLM 稳定错误」有我方自己的实验证据，不是生态借来的。
  3. **T1 探针法**：examples 字段的四型反例 + C2 事实上就是这个测试（reviewer's counterexample）——但 T1 是模型能力验收，A 要求的是**框架验收**（注入坏 S1 后看框架挡不挡），两者是不同的臂。
- **Bearing 探针化**（4-lens）：A 的验收可以完全机械化——T0 注入 `s1AlwaysGrant`（返回 grant、details 任意、永不 unknown），断言：V1 下 dispatch 被拒且控制事件留痕（复用 E3，adopt.go:444-461 的形态）；V0（现状）下 dispatch 放行（红测试证明缺口存在）。这是 30 行测试代码就能钉死的事。
- **对方的隐藏假设（critical thinking）**：A 的前提「事实是可核验结构化输入」在生产中不成立——事实是语义提取的产物。校验器重算 `months>3` 是纯函数，但 `months` 这个数是谁从原始材料里读出来的？若来自 S1 或其上游快照，校验器只验证规则应用，**提取错误原样穿透**（详见 §七 singularity 与 §十验证计划的 S1-ExtractionMiss 臂）。对方在 198232012:58 自己给出了三分法（明确算术/阈值→规则能力；语义事实识别/关系判断→Jev；无法证明→补证复核降级）——这个三分法承认了边界，但他们的反例 A 测试设计没有覆盖边界外的提取面。**我们要在验收里比他们要求的更狠一档**（这也符合我方「修复声明必须机械验证」的立法精神：他们要的探针 + 我们发现的新缝的探针）。

### 2.2 反例 B：事实缺失被当作没有风险

**对方设定**（198232012:116-119）：只拿到近 6 个月资料不能证明历史上无超 3 个月逾期；即使 Jev、S2、规则校验器一致，输入覆盖仍不充分；需验证证据覆盖声明及可信来源；承认边界：上游数据失真且无独立核验来源时框架无法凭空恢复真相。

**我方判定：半击中——「声明 vs 足迹」已有，「必需 vs 实有」缺失。**

- 已有面：judgment.schema 的 `resolution.on_missing_evidence`（:173-191，缺证不是自动否定答案）；T0 场景 2（e2e_test.go:295-341）走 gap→补证→复判；evidlog.CheckCoverage 做「声明查询 vs 实际足迹」差集（Missing=声明了没查的，Unaccounted=查了没声明的，evidlog.go:320-382）；0.2.0 路线图挂账 on_evidence_gap {gap_conclusion, queried, missing}（schema $comment:276，夏 round-2 待查事项封存件字段组）。
- 缺失面：**这是另一个差集**。evidlog 查的是「你声明的查询是否真的做了」（诚实性）；B 问的是「判断所需的证据覆盖是否声明并满足」（充分性）。veto 是无界时间窗（T0 修正后 unbounded，e2e_test.go:41-47），那么正确判断**必需**覆盖全历史的逾期记录来源——这个「必需」目前无处声明：conventions.evidence_sources 只是来源名单（:93-99），没有时间范围/必需字段/覆盖要求。6 个月数据+on_missing_evidence 不触发的原因：S1 看到的是「逾期列表为空」而无法区分「无逾期」与「没查历史」——**缺证被表述成了阴性证据**，这正是 B 的病。
- 修法（Fidelity 对齐夏裁决）：判断规格（或 0.2.0 输入快照 schema——D-01-05 已承诺同批交付，reply §二条件二）新增 required_coverage 声明（来源×时间范围×必需字段组）；采纳前机器可判 REQUIRED-vs-AVAILABLE 差集——与 evidlog 的 DECLARED-vs-QUERIED 并列两个正交检查。夏 round-2 的元原则（:172-176）「事前结构化优于事中裁量」就是这块的立法依据：覆盖要求在雇佣时刻写进规格，运行期机器判。
- 对方的诚实边界我们确认：REQUIRED-vs-AVAILABLE 检查不了「来源本身失真」。deepseek-harness SAFETY.md:8-14 的同款句式（"Even correctly enforced restrictions cannot protect resources the project is allowed to access"）——生态同样拒绝在此处承诺。B 的机器边界到「声明覆盖对账」为止，剩余按其 §三.1 走数据质量责任。

### 2.3 反例 C：首次结果错，快路径不断复用

**对方设定**（198232012:121-126）：R 场景保持原操作重试不重调模型不重复效果，但结果被认定有误后，当前状态读取应能看到纠错/失效信息；幂等契约仍返回原回执时应提供关联状态查询。K 场景不能把某客户错误结论推广给新任务；知识/方法撤销后对新任务停止适用。两句原则：「原始历史不可改，不等于错误结果永远有效；幂等身份不可偷换，不等于不能发起显式纠错。」

**我方判定：击中，但主体是已认领的 R/K 缺口——新增概念只有一个：「当前有效性」必须是投影。**

- 已有面（比对方可能预期的多）：
  - T0 场景 3（e2e_test.go:349-380）：新证据强制修订——**历史不可改**（`op-rev-1` 保持 completed）+ 新修订独立可归因（`op-rev-2-deny` adopted）——对方「生效后纠错」第 2/3 条（历史真实存在/关联新修订经重新采纳）的机器形态已存在，只是没有「关联」字段把它们连起来。
  - 场景 5（:430-459）：请求已发出后新证据不改判 in-flight 操作、新判断落为新修订——对方第 4 条（原请求按原身份等待、不得替代掩盖）的 14-A5 侧已钉（unresolved 一等态+never-auto-retry+对账出口）。
  - identity 的 BusinessRequestID + EvaluationRevision（adopt.go:163）——「同一业务请求的多修订」的身份基础已在。
- 缺失面（全部在 D-03/D-04 已认领清单内）：回执从不落盘（reply §三 D-03：bankAPISubmit 返回值仅作字符串比较后丢弃）；无等待驱动/终态观察者；知识消费路径零代码载体；读取面零授权检查。**新增**：无「当前有效性」视图——State() 只回机器态（completed），没有「该结果是否仍被后续业务视为有效许可」的查询面。
- 架构答案（系统论）：**不改机器**。纠错=新修订（新 operation_id、同 business_request_id）走完整采纳链（含 A 校验）——这天然被 identity 支撑；「当前有效性」= replay/projection 层按 business_request_id 聚合计算（最新已采纳修订=当前有效），**投影不写历史**。幂等面（同键同载→原回执）与有效性面（关联状态查询）是两个读，各答各的——对方的「两句原则」在这个形态下同时成立且互不干扰。这比给机器加 superseded 态更简（Simplicity），且不破坏「机器不解释业务语义」的章程。

## 三、OpenJiuwen 认知智能体经验碰撞（我方战场战绩）

### 3.1 PEV：防腐层三铁律 = 采纳边界的前置立法

pev-core-patterns.md:76-82（防腐层三铁律）：

> 1. LLM 输出进 Runtime 前必验证无例外（JSON schema / ID 存在性 / 参数合法性）
> 2. 验证失败不崩溃，降级兜底（sanitize + 兜底 plan + CONSTRAINT_VIOLATED 事件）
> 3. 原始输出入审计日志

**迁移判定：直接命中 A 的采纳边界形态。** S1 判决是「LLM 输出进 Runtime」的一个实例——现状 adopt.go 已做第 1 条的 schema 面（checkRequest）与第 3 条的账本面，**没做语义面**（防腐层的本义）。EDPA 的 checker 补语义面的 deterministic 子集；「降级不崩溃+CONSTRAINT_VIOLATED 留痕」映射到「校验冲突→复核路径+控制事件」——正好是 E3 控制事件的第二个用武场景（第一个是 14-A4 拒绝审计，adopt.go:444-443 注记「signature guard's every firing was traceless」的教训同样适用于校验器拒绝）。

另：auto4 教训（预防层消除触发条件优于 selfCorrect 事后修复，:53-61）对 B 的启示——**覆盖声明在开发态进规格（事前）优于运行期判缺证（事中）**，与夏元原则同构，三战收敛。

### 3.2 EDPA-alpha：DeterministicChecker 是 A 的成品形态

edpa wiki :51-52（确定性兜底铁律「规则 > LLM judge」）、:219-237（GroundTruthVerifier 分派：checker matches→纯计算；不命中→keyword 兜底）。关键结构迁移：

- **SPI 归属声明**：checker 声明 own 哪些 criteria（`matches`）——映射到判断规格的 per-rule verifiability class 声明（formalizable→checker；semantic→Jev+抽样；unattainable→复核）。对方 §三.1 三分法与我方 EDPA 分派是同一结构的两次独立结晶。
- **keyword 兜底的诚实边界**：不命中 checker 的 criterion 落到弱验证——这正是「能检查的必须检查，不能检查的受控处理」的已有实现。NGA 移植时兜底不应是 keyword（credit 场景没有可 keyword 的判据）而是「复核/受控交接」通道——形态更强，结构同型。
- **坑位教训**（edpa wiki :1183-1196）：autoconfig 用空 checker 构造 GroundTruthVerifier、不自动发现 @Bean——**checker 注入是宿主显式装配**。迁移到 NGA：校验器的装配与规格版本绑定必须是显式契约（挂 versions.rule），不能 ambient 发现——否则校验器与 S1 消费的规格可能静默分叉。

### 3.3 LoopForest：VetoRail + GoalContract 两件直接可移植

- **VetoRail**（VetoRail.java:22-40）：写入契约白名单 veto，bait 执行率 OFF 50%→VETO 0%（跨模型一致）、SAT 不伤。**零提及纪律**（拒绝消息永不点名哪个字段多余——提及即诱导，72 run 双模型验证）与夏 round-2 补证单表述纪律（:87-93「只写缺什么证据，不写期望什么结论」）独立收敛——NGA 的复核反馈通道必须继承这条：**校验冲突的反馈不得向 S1 泄漏期望判决**，否则下一轮 S1 顺着泄漏改口，校验器就变成了提示注入器。这是移植中最容易踩的缝。

## 六、五层概念拆分批判

对方五层（198232012:35-41）：判断正确性 / 判断一致性 / 重试幂等 / 执行正确性 / 业务实际结果。

### 6.1 拆分本身：接受，且是对我方 T1 的一记正打

我方 T1 的门槛设计实际把「一致性」当成了验收主力（CONSISTENCY pairs C1↔C5、C2↔C4，t1_llm_test.go:28-31），正确性靠 expected-verdict 匹配——但两者在 gate 集合里没有概念分立。对方的表让我方术语表（TERM-01）多了一个必须分立的词族。**特别是「一致地犯错仍然是错；把它持久化，只会使错误更稳定」（:31）一句同时击中我方幂等层的语义盲区**：reused 事件的 Detail 写着 "retry under the same key and digest"（adopt.go:300）——机器确实在把「同一答案」神圣化，这正是 A+C 的复合土壤。

### 6.2 两个缺行（分类法批判）

1. **判断输入充分性（证据覆盖）没有自己的行**。它被埋在「判断正确性」的定义里（「在指定语义规约、事实范围和参考时点下，结论是否成立？」）。但 B 的全部要点是：**available-facts 下的正确 ≠ required-facts 下的正确**。输入充分性有自己的机器判据（REQUIRED-vs-AVAILABLE 差集——可判！）、有自己的责任者（规格作者声明/管理面批准）、有自己的失败形态（缺证误判为阴性证据）。它应该是第六行（或替换「业务实际结果」的层级位置）。**这是对方分类法最实质的遗漏——而它恰好是 B 反例得以成立的概念基础，对方的表没有为它留位，说明 B 的机制化在他们自己的框架里也还没想透。**
2. **规格正确性（规约本身是否正确）没有行**。表的第一行把「指定语义规约」当成无条件前提——「错误规约」只在 :105（纠错归因清单）里出现一次。一个完美校验器执行错误规格=稳定的、全验证的错误判决，五层表**无法表达这个失败模式**（每一层都「通过」）。规格正确性的验证方法是 examples 回归探针+管理面审批（夏 round-2 规格失灵三情形 :41-49 是治理终点）。对方问题 1 问「正确性的依据和最终责任」——他们自己的表答不了，因为答案在表外。

### 6.3 「层」的隐喻批判（系统论预备）

五项不是**栈**（stack），是**五个正交验证主体**：一次决策同时携带全部五个属性，各自有验证方法（正确性=重算/治理、一致性=语义等价对、幂等=同键同载断言、执行正确性=参数/时序/授权断言、结果=对账）。叫「层」会诱导「正确性层加在哪一层之上」的错误问题（我们在任务里也差点这么问）。正确问题是**矩阵**：每个验证主体×在哪个环节（快照形成/采纳前/派发前/终态/事后）×用什么方法×谁负责。「正确性层加在哪」的系统论答案见 §九。

## 七、singularity 总判（分叉博弈）

### 7.1 全盘采纳五层+独立校验：问题被重定义，且重定义正确——但产生三个可达坏状态

**重定义（正向）**：「幂等」卸载掉它从未合法承担的正确性语义；「框架保证」从「保证执行如判决所述」升维到「保证形式化约束经独立重算」——这是从**忠实执行**到**受控真值**的范式迁移，问题确实被重定义了，且迁移方向与我方六条冻结原则（原则 3「判断、分支选择和推进依据进入记录」）兼容。

**坏状态 1（校验器暴政）**：错误校验器（规格 bug 或实现 bug）以机器权威批量拦截**正确**的 grant——失败模式从「模型错、系统跟随」翻转为「校验器错、系统阻断」。对方 :138 自己点了这个病（「不能通过一律拒绝伪装正确」）。防线：a) 校验器 conformance 于规格 examples（100% 通过才可装配）；b) 错误拒绝率进 KPI（ledger-native）；c) 校验冲突走复核而非终拒（fail-to-review 而非 fail-to-deny）。注意 hermes 的 fail-OPEN 选择与我方 fail-closed 传统的张力——**采纳边界 fail-closed（拦住再复核）、复核通道 fail-open（复核不可达时按风险策略）**是折中形态。
**坏状态 2（Jev 架空）**：若 formalizable 子集覆盖了判断的全部（credit demo 恰好如此——veto 就是全部），校验器重算=判决本身，S1 沦为装饰打分。对方 :58 明说不要这个。防线：校验器只 own per-rule 声明的 verifiability class；**语义提取（这份材料记录的是不是一次 4 个月逾期）永远留给 Jev**——credit 演示的「结构化事实」在真实系统里是 Jev/S2 的产出。这个分界就是 §〇 的关键保留。
**坏状态 3（提取穿透）**：校验器消费 S1 提取的事实→规则应用被验证、提取错误原样通过→系统带着「已独立校验」的印章放大提取错误。这是对方测试设计的盲区（他们注入坏 S1 但喂干净结构化事实）。防线：事实引用协议（引用 ⊆ 卷宗，ReportChecker fidelity 移植）+ 抽样独立重提取审计 + 诚实边界声明。

### 7.2 全盘拒绝（零采纳）

可达坏状态：对方的故障注入测试（:114「验收错误授权效果是否被挡住，而不只是验收模型能否在样例上答对」）描述得如此具体，**他们必然会跑**——V0 形态下这是必死之局；且 TERM-01 的词族分立（reused/unresolved/conflict 已做）与「正确性不分立」形成刺眼的不一致，谈判位损失。零采纳没有可达的好状态。

### 7.3 部分采纳（实际推荐）

V1（确定性校验，formalizable 子集）+V3（规格探针）先行、V2（双模型）按风险配置、纠错语义并入 R/K。**这个组合下每个坏状态都有具体防线，且不引入新的全局组件**——Simplicity 通过。

## 八、第一性原理

挖到不可再让的前提：

1. **形式化约束+可信结构化输入 ⇒ 可计算真值。** 验证=重算，这是算术，无需更深的理由。不可再让的前提只有两个：(a) 规格正确（治理前提——examples 回归+管理面审批，夏规格失灵三情形为治理终点）；(b) 事实提取正确（语义前提——只能部分核验）。**第一性结论：正确性架构=按可验证性类别分区，分区边界在判断规格里按规则声明。**
2. **开放语义判断不存在短于权威上诉（人工）的计算真值。** 所以开放语义的「正确性」是治理关系（剩余不确定性归谁），不是技术属性。对方 :43-45 的四句要求（能查必查/未满足不生效/剩余受控/错误可纠）正是把技术属性正确翻译成治理关系的尝试——**这个翻译是对的**，我方接受的是翻译结果而非任何技术幻觉。
3. **幂等是恒等性质（同键→同记录），正确性是真值性质——正交。** 从这对正交性直接推出纠错的形态约束：幂等持久化「当时所判」，故错误处理只能是**加性修订**（新 operation_id、同 business_request_id）而非改写——这与对方「原始历史不可改，不等于错误结果永远有效」（:126）和 T0 场景 3 的既有形态三点收敛于同一条第一性结构。**「当前有效性必须是投影」不是设计偏好，是幂等律的推论。**
4. （对我方自己的）**保证的强度不得超过判据的机械性**：可 100% 断言的只有机械判据（注入坏 S1 后必拦）；统计性断言（模型漂移率、复核有效率）必须配对测量（XM2 同日配对律）且带半衰期标注（ReAnchor 立法）。任何把统计保证说成机械保证的回复都是新的病灶。

## 九、系统论：正确性检查挂在哪一层

**答案：不新加「层」——加一个「环节×判据」矩阵的填充。**

```
固定图（已冻结原则1）：获取/核验事实 → 输入快照(0.2.0) → S1 候选 → [新]独立校验 → 采纳 → 派发 → 业务API → 终态
                                    │                    │        │        │
                                    │                    │        │        └─ 14-A4 权限复检（已有）
                                    │                    │        └─ Adopt：载荷含校验维度（新增）
                                    │                    └─ V1 校验节点：读规格(formalizable子集)+快照 → 重算判决
                                    └─ REQUIRED-vs-AVAILABLE 覆盖对账（新增，机器可判）
```

**耦合分析**：
- 与幂等层：校验结论进 payload digest——同判决→同 digest→reused（正确幂等）；新校验结论→新修订→新键（纠错路径）。**与 conflict 语义天然组合**：校验结论变化而 operation_id 不变=changed payload under same key=conflict（adopt.go:277-291 现有行为），提示纠错必须走新修订键——机器现有语义直接替我们执法。
- 与授权层：正交双闸（grants 管 effect、校验管 adoption），各自 fail-closed，互不越权。
- 与判断层：**规格是唯一真源、双消费**——S1 prompt 与校验器共读同一 spec 版本（挂 versions.rule 钉照）。这是 EDPA 坑位教训（空 checker ambient 装配分叉）的防线。
- 与 R/K：首次采纳跑校验；reuse 返回原回执**不再校验**（幂等的本义）——所以纠错必须经新修订重新走全链。「当前有效性」由 replay/projection 按 business_request_id 聚合计算，**投影不写历史**。
- 与 E3 控制事件：校验拒绝=新控制事件类别（第二个 signature guard 场景——每次校验拦截可审计）。
- 与夏裁决面：覆盖对账=差集告警的姐妹件（两个不同的差）；复核反馈=零提及纪律（VetoRail+夏 2.3 三源收敛）；B 转级=质证三出口（A 定向补证→B 无法判定→C 人裁，round-2 §二）已把「校验失败去哪里」的路径图给全了——**对方 How 段的「补证、矛盾、校验失败、需复核等路径同样预先发布」与夏的流水线是同一张图**，两轮外部输入在我方裁决底座上合流了。

## 十一、最深刻发现（自评三条）

1. **独立性陷阱**：反例 A 的「独立校验」的独立性上限=事实提取来源的独立性。校验器消费 S1 自己的提取结果时验证的是规则应用、继承的是提取错误——对方的测试设计（注入坏 S1、喂干净结构化事实）会制造虚假安全感。正确性层的保证边界必须声明到提取层为止，且验证计划必须包含 s1ExtractionMiss 臂（对方没要求、但比对方要求的更狠）。
2. **五层表的两个缺行**：输入充分性（B 的概念基础，可机械判据 REQUIRED-vs-AVAILABLE，对方自己的表没为它留位）与规格正确性（完美校验器执行错误规格=全验证的稳定错误，五层表无法表达）。「层」应改读为五个正交验证主体的矩阵。
3. **三战收敛+生态同构**：我方 VetoRail（bait 50%→0%）/EDPA（规则>LLM judge）/SmartResearch（零 LLM 判定器）与 hermes 质量门短路 judge/codex exec_policy 独立收敛于「确定性检查在 LLM 判决之前」——对方要的不是新发明，是这个已交付三次的机制的企业治理化。真正的新东西只有纠错与幂等的共存语义（「当前有效性必须是投影」），而它是幂等律的第一性推论、我方 T0 场景 3 已半承载。

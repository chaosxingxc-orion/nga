## 攻击 1（E1）：「manifest 单源」的真实性

### 最强反方论证
生成器只覆盖七增长族计数行；基座/evidlog 的计数、以及文档其余三处钉，没有任何机制强制 manifest 与目录一致。pi 先例的灵魂是「重新渲染 == 已提交产物，否则 CI 红」——如果本仓没有这个不变量，manifest 不是单源，是**第五份手抄**，而且是不被任何东西检查的那份。

### 证据
1. **生成器零消费者**：`grep -rn corpus_manifest` 全仓只命中 `tools/corpus_manifest.py` 自身——没有测试重渲染对拍，没有脚本调用。且 `agent-festival/` 仓**没有任何 CI**（`.github/` 不存在于仓内；worktree 根的 `sync-gitcode.yml` 只做镜像同步不跑测试）。碰撞报告主题 1 的死线——「stale 测试**挂在 CI**（不挂 CI 的生成器等于死代码）」——在无 CI 的仓里结构性落空。
2. **已提交块 ≠ 生成器输出（出生当天即漂移）**：实测 `python3 tools/corpus_manifest.py` 输出 10 行（`增长族合计`/`基座契约/信封`/`全仓合计`），而 `docs/conformance-fixture-format.md:25-38` 的已提交块是 **12 行数据行**：标签被手改成 `增长族合计（非密钥库）`/`基座契约/信封（非密钥库其余）`，且 `基座契约/信封 | 50` 与 `全仓合计（含密钥库） | 200` **各出现两次**（:35-38）。块头明写 `do not hand-edit counts below`（:23-24）——被违反了。数字今天全对（146/50/200 三面一致，实测），但 pi 形态的字节级不变量在 HEAD 上为假。
3. **「消灭手抄第四副本」未发生**：doc §一 的人写计数表（:9-18，含 `其余` 行）原样健在，intro 句（:3 `200 件/146 件`）也是手写数字。今日实际计数面：§一 人写表、intro 句、manifest 块、Go `cmd/*/main_test.go` 摘要钉（如 compose/main_test.go:502 硬编码 `10 must-accept + 36 must-reject`）、Py oracle 元组钉（ledger.py:290 硬编码 `(10, 26)`）、schema/README 散布计数、java README 计数——**≥6 面，不是 1 面**。

## 攻击 2（E2）：模块路径的残留与 CWD 探针

### 最强反方论证
改 module path 只动了标识符，真风险在两处：(a) FindSchema 的相对探针在 go test 之外（仓根 `go run ./cmd/x`、任意 CWD 安装态）找不到或找错 schema；(b) go.sum/文档/脚本残留旧路径；且新路径若不可 go get，「域名化」的目的落空。

### 证据
1. **残留 = 0**：全仓 grep `festival-dev`（含 go/schema/docs/examples/README）零命中；`go/go.sum` 全部四依赖 + x/text，无旧路径条目；新路径 import 47 处全部命中；`go build ./...` + `go vet ./...` + `go test ./...`（20 包，-race 亦绿，实测）。
2. **「仓根 go run」前提本身不成立（我方攻击被仓结构化解）**：module 根在 `agent-festival/go/`，仓根无 go.mod——`go run ./go/cmd/ledger` 在仓根直接报 `go.mod file not found`（实测）。这不是回归，是模块边界；约定调用位是 `go/` 目录，实测 `go run ./cmd/ledger` 全绿（探针 `../schema` 命中）。
3. **任意 CWD 安装态 fail-closed（对「找不到→静默错」的攻击失败）**：`go build -o /tmp/rt-ledger ./cmd/ledger` 后在 /tmp 运行 → `[ledger] schema not found`，exit 1（实测）。FindSchema（schemalib.go:57-67）与 init 探针（validate.go:46-58）找不到即空值，检查器拒绝服务而非跳过校验。
4. **真实残留风险（范围外但需登记）**：(a) 新路径 `github.com/openjiuwen/agent-festival` 在 GitHub **404**（gh api 实测）——`go get` 今天不可达，「可 go get 路径」是预期态不是现状态，且既不是 fork（yaojun01）也不是 MR 目标（xingchao_ml/nga），是第三处尚不存在的地址——pi 的 `https://pi.dev/schemas` 教训（路径钉进消费方）适用于此；(b) 探针序 `../../schema` 先于 `"."`——理论上层存在同名 schema 目录会静默装错版本（基座继承行为，非本批引入）。

### 反稻草人自批判
攻击前提「仓根 go run」被结构否证，这部分是我方稻草人——如实记分。404 发现是真伤但属于 E2 命名范围（「可 go get 路径」）的边缘：03 批文写了「或等价」，且域内标识符唯一性本身已达成。

### 裁定：**免疫**（对「零残留」子命题），附一条范围注记（go-get 可达性是预期态，落库时点未定）。

### 对 H_exec 分数影响
0（±0），注记不扣分。

## 攻击 3（E3）：键迁移的双轨兼容

### 最强反方论证
老英文文本保留 = 双轨，但「键是规范面、文本是兼容层」如果只活在提交信息里，新消费者读不到——α 攻击面（键改了钉没跟）只是被「套件今天全绿」暂时压住，不是被机制消灭；且双轨无 sunset，违反碰撞修正 5。

### 证据
1. **键面声明成立（对「键不在首段头部」的攻击失败）**：13 个唯一键双侧同集（Go 14 处 = 13 唯一 + 1 处复用；Py 13 处），机械扫描 `[LEDGER.*]` 是否都在消息首段头部：**Go not-at-head=0 / Py not-at-head=0**（实测）。
2. **钉迁移成立**：17 个夹具文件钉已键化（`grep -rl "LEDGER\." schema/examples/` = 17），ledger 代码规则族逐夹具核对全部 `LEDGER.*` 钉（含 R2 补迁的 same-key-digest 与 grants 三件）；剩余短语钉（`grants_at_decision`/`payload_digest`/`effect` 等）是 schema 引擎消息的字段名钉——提交信息声明的「字段名=中性」分类成立，双侧套件绿佐证无陈旧短语钉。
3. **规范面声明缺席（攻击命中）**：`docs/conformance-fixture-format.md`——跨语言合同的正式载体——**零处提及** `[LEDGER.*]` 键约定（grep 实测 0 命中）。§四 给「任何语言 X」的接口契约里，错误匹配面只写了 `_expect_match` 子串，没说该子串应取键不取文本。新消费者唯一的键知识来源是读 Go 源码或 spike 的 `LedgerChecker.java` 重实现——这正是 03 预登记 α 面警告的隐式约定形态。

### 反稻草人自批判
最强调防：套件红绿本身就惩罚「键改了钉没跟」——迁移期任何一侧漂移即红。成立，所以是轻伤不是重伤；但套件只保护仓内，不保护**仓外消费者**（Java SDK 正是要保护的对象），而 §四 恰是写给他们的那份文档。不构成稻草人。

### 裁定：**轻伤**

### 对 H_exec 分数影响
－1。修复=§四 加两句 + sunset 一行。

## 攻击 4（E4）：奇数孪生夹具的折损域声明

### 最强反方论证
合同文本钉 float64 判定域——但若夹具字面量本身是偶数孪生 ..992.0（float64 精确可表示、无折损），则精确域与 float64 域对它的判决完全一致，夹具不钉任何东西；而四处叙事（夹具 _expect、Go 测试注释、格式文档 §三、README）都在描述 ..993.0。R2 的 B1 修过一次——若最后一次提交悄悄改回，全绿套件一件都不会红。

### 证据
1. **HEAD 字面量 = ..992.0（击杀实锤）**：`schema/examples/ledger/valid/seq-odd-float-twin.json` 第二事件 `arbitration_seq: 9007199254740992.0`，而同文件 `_expect`（:102-103）自称 `9007199254740993.0 ... pins the FOLDING itself`。git 考古：4c8817a 出生即 ..992.0（R2 评审 B1 定罪，r1-exec-review.md:31-35）；4e1785a 修为 ..993.0（diff 实证 `..992.0 → ..993.0`）；**db42cd6（末笔，提交信息自称「件6 R13 尾批——注释/文档/边界修正」）把字面量悄悄改回 ..992.0**（diff 实证），提交信息对此零字提及。
2. **四处叙事四处假**：夹具 `_expect`、`go/internal/ledger/ledger_test.go:110-116` 注释（`9007199254740993.0 ... is judged as its even twin`）、`docs/conformance-fixture-format.md:70`（§三 判定域声明整段描述 ..993.0 折损）——三处（含 schema/README 同源表述）描述的夹具不在 HEAD 文件里。
3. **无机械钉能抓住它（套件全绿是必然）**：`TestOddFloatTwinPinsFoldedDomain`（ledger_test.go:117-132）只断言 ACCEPT；grep 全 Go 测试树无任何对 `9007199254740993` 字面量的字符串断言。/tmp 实验双向验证：HEAD（..992.0）全绿；改回 ..993.0 后 Py oracle `10+26, 0 failures`、`go test ./internal/ledger/ ./cmd/ledger/` 双绿——**两个字面量都绿，绿不分辨对错**。
4. **折损力学本身为真（对「Go Float64() 行为」的攻击失败）**：/tmp 探针实测 `json.Number("9007199254740993.0").Float64() = 9007199254740992.0`（round-to-nearest-even），甚至纯整字面量 `9007199254740993` 的 Float64() 也是 ..992——float64 域根本装不下 2^53+1，E4 的域声明机制描述正确。死的是夹具，不是力学。
5. **同一文件同一病第三次**：出生假（4c8817a）→ 修复（4e1785a）→ 静默回退（db42cd6）。R2 修复批提交信息自己写着「声称-现实漂移再犯」——它在治的病，在同批的收尾提交里第三次复发，且藏在一次无关主题的提交里。

### 反稻草人自批判
最强调防：..992.0 字面量仍走「float 语法整值归一化」路径，夹具并非零内容；且「两域本就都 ACCEPT ..993.0（叙事自己承认 exact reader also accept），折损分叉面由 float-beyond-2^53 拒绝侧钉」——即奇数孪生夹具的区分力本来就弱，回退造成的增量伤害有限。前半成立（所以修复不是重做是改一行），后半不成立：`_expect` 末句明写 `This fixture pins the FOLDING itself`，HEAD 文件钉的不是折叠——叙事对文件的描述为假是客观事实，与区分力讨论无关。非稻草人。

### 裁定：**击杀**
H_exec 子命题「奇数孪生夹具真折损」在 HEAD 为假。修复路径已实测：一行改回 ..993.0（双侧全绿）+ 补一个**字面量级机械钉**（如 Go 测试断言原始字节含 `"9007199254740993.0"`——叙事钉活不过一次无关提交，字节钉才能）。

### 对 H_exec 分数影响
－3。这是本红队唯一击杀，且病根不是知识（B1 判决书就在仓里）而是**修复声明未被机械复验**——db42cd6 违反了 V2 立法「修复必须机械验证」。

## 攻击 6（E6）：取证日志与件4 账本的职责边界

### 最强反方论证
两个 JSONL append-only 流，消费方拿到一条裸记录怎么知道进哪本？混进去会怎样？密度+覆盖双向 OK 是不是只有单侧实现、单侧钉？

### 证据
1. **混流攻击被 schema 结构杀死（我方主攻击失败，如实报告）**：/tmp 机械探针——evidlog doc 对 event-ledger schema 校验 → `rejected: Additional properties are not allowed ('events', 'ledger_version' ...)`；反向同理。两 schema 双侧 `additionalProperties:false` + required 集互斥（seq/tool/selector/caller/at vs event_type/arbitration_seq/identity/...），`$id` 不同（`.../evidlog/0.1.0` vs `.../event-ledger/0.1.0`）——混入的记录在验证时**双向响亮拒绝**，不存在静默混流。
2. **分家声明在场**：`go/internal/evidlog/evidlog.go:6-10` 包文档第一段明写「Deliberately NOT the piece-4 event ledger ... Two atoms, two logs」——碰撞修正 3（γ 面）落实 ✓。独立性实证：evidlog 只 import schemalib，不引 adopt/ledger 包（imports 实测）。
3. **密度面双侧钉 ✓**：seq 稠密性规则 Go（evidlog.go:183 `a gap or a foreign writer`）+ Python（evidlog.py:21-27 镜像）+ 夹具 seq-gap.json 三层钉。
4. **覆盖面 OK 双向是真双向、但只有单侧实现（攻击部分命中）**：`CheckCoverage`（evidlog.go:145-163）OK = Missing 空 **且** Unaccounted 空（hidden exclusion → OK=false，m-1 补的钉）；Go 单测 `TestCoverageMissingAndHiddenExclusion`（evidlog_test.go:62-88）双向钉 ✓。但 **Python 侧零覆盖实现**（evidlog.py 只有 schema+密度，grep 实测）、语料夹具零覆盖面夹具、Java spike 不可达——「覆盖双向 OK」的双向指声明方向，不是实现方向；README 只声称「schema+密度规则双侧镜像」，未虚报，但 OK 语义无跨语言钉。
5. **单写者假设未显式声明（攻击命中，小）**：碰撞修正 4 要求「单进程假设，多写者未定义」写进 schema 文档——evidlog.go/schema 里只有间接暗示（`writer-allocated`/`foreign writer` 措辞），无显式「多写者未定义」句。seq-gap 错误消息暗示了 foreign writer 可检测，部分缓解。

## 攻击 7（E7）：三边类型与 evidence_gap 提案的种子正确性

### 最强反方论证
9 格文法（3 类型 × 3 属性）在 0.2.0 的验证预算没人预算过；如果 0.2.0 只落部分属性，边文法里没落的部分语义悬空；碰撞修正 2-4（9 格表/逐格夹具/成熟度标注）是否被静默丢弃？

### 证据
1. **9 格文法按设计不存在（对「预算不足」主攻击的化解）**：05-edge-grammar-prior.md §一 明写三属性是「**受控交接边的三属性**」（:26-28）——属性是类型参数不是正交轴，恰是碰撞修正 2 优先推荐的参数化形态（EphemeralValue.guard 先例）；文法不是 9 格，是 3 类型 + 1 类型上的 3 属性。0.2.0 验证税因此按 4 个有意义格计，不是 9。**但**：文档没有任何一句说「三属性挂在 collaborative/adversarial 边上非法」——格间合法性在 schema 层如何拒绝（碰撞修正 2 的后半句「非法格要在 schema 层拒绝」）完全未指定。一个规格作者把 `sealed_manifest` 挂上对抗边，提案层无裁定。
2. **0.2.0 最小实现面静默丢掉可证伪性闸门（本条最锐利的发现）**：§二 :77 明写夏裁决点②「**可证伪性是准入门槛**」，准入机制 = `confirm_query`/`falsify_query` 对（:96-99 写不出即拒收）；而 :117-119 的 0.2.0 最小面只有三字段 `{gap_conclusion, queried, missing}`——**没有证伪查询字段**。两条机检分界线之第 2 条（可证伪性门槛）在 0.2.0 interim 无从判定：写不出证伪查询的假设（「这客户感觉有问题」）能通过三字段 schema。文档说四字段是「升级目标」，却从未承认 interim 期闸门缺席、也未写任何补偿（如 interim 期 gap 一律人工复核）。夏的第二轮裁决就写在同一份文档里，最小面与之直接矛盾而未被点破。
3. **每格夹具/成熟度标注缺席（轻）**：碰撞修正 4 要求每格标「spec-only / 有夹具 / 有双侧实现」——文档只有全局头注「本件是设计文档，不是实现」（:3），无逐格标注。每类型一句行为差异 ✓（§一 表格语义列），每格一夹具因 spec-only 而不适用（03 OUT：E7 是提案不是发出）——此项部分豁免。
4. **种子方向本身有强支撑（对「种子错误」的攻击失败）**：evidence_gap 一等症状类型（langgraph 显式结果类型先例）、A/B/C 出口与件2 状态机同构映射（:67-71）、补证上限预注册位置（不归猎人也不归运行期）、反馈污染防线（:61-63）——每一项都有裁决或先例锚，无无锚设计。

### 反稻草人自批判

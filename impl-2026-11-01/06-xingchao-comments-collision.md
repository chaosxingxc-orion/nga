## 一、逐点碰撞

### CP1｜E7 三态映射 A↔adopted / B↔unresolved / C↔conflict（评论① §4 + 六问 1）

**对方论证**：unresolved 的机器语义是「外部执行结果未知」（adopt.go:58 注释 `dispatch outcome unknown (timeout / crash) — first-class, never auto-retried`）；质证 B 出口是「模型证据不足」。恢复后无法从状态本身区分该补证还是该等 API 对账——每个消费者被迫写隐含分支。另指出「声明与日志矛盾」可机器检测，05 文档「无机器判据」表述过宽。

**4-lens 检验**：
- **Simplicity**：单枚举承载两种语义=状态重载。系统动力学视角：短期省一个枚举，长期在恢复/授权/审计三个消费点各长一个隐含分支；分支的判定依据不在状态里，必然催生影子枚举（unresolved_reason 类字段）——省下的词汇量加倍还回来。对方的三组状态分层（任务工作阶段/决策问题/业务请求执行）各自封闭枚举、共享基础设施，符合邢超自己「不要求三个服务或三套执行引擎」的边界，也符合夏元原则（结构化声明）。
- **Consistency**：05 文档把 C 映射到 conflict 是类别错误的一半——conflict 在 ledger 里是 adoption 同 key 异载的 **outcome**（adopt.go:267），不是 State（State DAG 只有 adopted/dispatched/unresolved/completed/failed）。映射表三行有一行映射对象都不存在。
- **Bearing（变异-RED）**：对方的场景表四行（无完整材料/请求在途/声明与日志矛盾/同 key 异载）合法后续动作集合两两不同——任选两行合并到一个状态，恢复逻辑必然需要状态外信息。这个反例是可执行的（对方评论②的 torn-tail 探针就是第一行的实例化，见 CP6）。
- **Fidelity**：**关键归属事实——这个映射从未进入夏的裁决**。夏第二轮裁决建立的是质证协议本体（A→B→C 出口、预注册上限、补证单纪律）；「与件2 状态机的映射」段落是 05 文档标注的「碰撞分析发现的深层同构」，作者是我方。撤回它不损夏裁决一分。

**singularity**：坚持映射→影子枚举不可避→问题从「要不要复用状态机」重定义为「一个枚举能否承载两种恢复语义」。**可达奇点，对方胜。**

**裁定：接受撤回「直接等同」，精准划界保留三件**：①质证协议 A/B/C 本体（夏裁决，不动）；②「可共享事件存储、转换库、控制基础设施」（对方原文自己的边界）；③衔接设计：质证协议是 S1↔S2 协作协议、三态分层是对象生命周期管理，两者正交——A/B/C 出口挂载到新分层的方式属用户×xingchao 工程协商，我方后续给出衔接设计稿；定稿后知会夏（协议面出处人），衔接中发现真语义冲突再升级请裁。「无机器判据」表述同步收窄为：矛盾检测机器可判（件7 evidlog 六道门正是干这个的），矛盾的原因调查与最终处置归人。

### CP2｜元原则「人裁产出=规格补丁、单向收敛」（评论① §9 + 六问 5）

**对方论证**：坏数据、一次性例外、信任事件、普遍性语义缺陷是不同情况——都可成案例，但只有适宜复用的结论才进规格候选；候选需评估+授权发布；不能自动改变当前任务。

**4-lens 检验**：
- **第一性原理**：夏元原则的真实意图是裁量要有结构、有去向、可追溯、递归止住。对方修法保留全部四项，只把「落回」从自动改为「落回候选池并走发布门」。夏原文「下次同类案件回归字段化通道」确实隐含补丁已生效——语义模糊点真实存在，对方把它挑明。
- **Consistency（我方硬伤）**：我方自己实现了 release 采纳入口（件5），元原则却让人裁产物绕过发布流程直接生效——**同一个仓里两套生效语义**。这是比对方任何论证都硬的自相矛盾证据。
- **系统动力学**：夏版本=快收敛环；对方版本在环上加评估+发布缓冲。缓冲降低收敛速度，但阻断「个案噪声→全局政策」的正反馈通道。信任事件类人裁结论（「此 S2 不可信」）是案件事实不是规格语义，进规格即污染。高风险域缓冲的期望收益为正。
- **Fidelity**：六问 5 的「首版人工完成组织流程，机器面保留关联与证据」与我方 C3（M15 移出首版门、进化环外置）同向——hermes-self-evolution 实机佐证（README:76 PR human review never direct commit、:74 no mid-conversation changes）。此点双方已收敛，可先落锤。

**singularity**：坚持自动落回→个案污染通道+与我方 release 件矛盾→问题从「补丁要不要落回」重定义为「落回是否等于生效」。**可达，对方胜**——修法不推翻夏元原则，是精确定义：**人裁产出=规格补丁候选（candidate），生效必须经评估+授权发布，不改变已采纳决策与在途任务**。裁决权在用户×xingchao；定稿后知会夏（元原则出处人），衔接未见到真语义冲突。

### CP5｜umask 首写 0644 vs 0600（评论② P1-1）

**双方裁决现状**：我方 L9/L14 裁决=保留既有权限（0640 保持面）+首写 0644（os.Chmod 绕 umask by design，审计可读性记录在案）。对方=首写 0600 保守默认+既有保留（我方 0640 保持面对方实测通过）+宽读取走显式部署配置+Stat 非 NotExist 报错。

**4-lens 检验（诚实呈现双面）**：
- **第一性原理**：审计可读性（我方 0644 的理由）是**部署形态**的属性，不是组件的属性。组件在无授权信息时自行决定 group/other 可读=组件替部署方做了授权决定。
- **Consistency（我方内部不自洽）**：0640 保持面的裁决哲学是「尊重 operator 显式设定」；首写 0644 的裁决是「替 operator 决定」。两个裁决合在一起立场分裂。对方的 0600+保留方案在两个面上统一为同一哲学：**组件不替部署方做可见范围决定**。
- **Bearing**：对方对照表是可执行反证（umask 077 下 MR#1 0600 通过 / MR#2 0644 失败）——MR#1→MR#2 的行为变化本身就是回归事实。探针已附，可直接收编为永久探针。
- **对方附带缺陷成立**：我方代码 `if info, err := os.Stat(l.path); err == nil { mode = ... }` 把 NotExist 以外的 Stat 错误（权限拒绝/路径损坏）静默吞掉回退 0644——应显式报错。
- **我方立场的残余价值**：审计可读性需求本身真实（L9 初衷）。对方方案下它的正道=显式部署配置/授权（组件提供 mode 配置项或部署方 chmod 一次）。需求保留，达成路径更换。

**singularity**：坚持 0644→每个 umask 077 宿主都要补丁（组件裁决迫使全宿主补丁）；0600→需审计可读的部署方显式表达一次。**问题重定义为「谁有权决定可见范围」——可达，对方方案占优。**

**裁定建议（待用户终裁——用户此前裁过 0644，必须重新裁决不能自动翻转）**：接受 0600 保守默认+既有保留+Stat 错误显式报错+审计可读走显式配置。若用户维持 0644，则对方 P1 无法关闭、MR !2 继续被挡——这个后果要在裁决时知道。

### CP6｜受损尾恢复重复 dispatch（评论② P1-2）

**事实**：行为 MR#1 已存在（对方如实声明非新回归），但 adopt.go:131-149 的 TORN-TAIL DOCTRINE（HEALS + lossy-but-safe）声称安全，反例不支持该保证：Adopt→Dispatch→截断 dispatch 行→Open 恢复 adopted→再 Dispatch 仍 dispatched（执行许可重发）。

**我方 HEALS 论证的漏洞（自查）**：注释声称「a re-dispatch of an external effect is exactly the 14-A5 unresolved first-class case」——但 14-A5 的前提是 dispatch 事件**在账本里有记录**（outcome unknown），重新 dispatch 是对未知结果的再确认；torn-tail 场景 dispatch 记录**丢失**，机器回到 adopted 再发许可，不是再确认而是首次许可重发。组件内部无法区分「恢复到 adopted 因为 dispatch 从未发生」与「因为记录被截断」——与 CP1 同根：状态不携带恢复原因。

**4-lens**：
- **Simplicity**：若 HEALS 的安全论证（状态机自修复）不成立，adopt/evidlog 双 doctrine 分叉的存在理由动摇——两包注释互相指认的分工边界需要重写。统一到 evidlog 形态（检测+拒绝+诊断）=一个 doctrine，更简。
- **结构预防优先（本仓立法）**：拒绝+显式恢复流程让「无诊断地恢复执行许可」在结构上不可表达，优于任何守卫补丁。
- **Bearing**：对方探针（TestNGAReviewTornDispatchTail）可直接收编为永久探针，三选项任一都可被它验收。
- **诚实面**：对方三处限定（非新回归/不声称 atomic rename 会产生半行/不声称探针造成重复授信）全部克制准确——这是高质量的对抗复核，值得在回应里明说。

**三选项初判（待用户终裁）**：最小方案（Open 检测损坏尾→拒绝恢复为可执行状态→保留原始文件与损坏证据→返回诊断，恢复走显式流程）在 Simplicity/结构预防/与 evidlog 一致性三轴占优；代价是外部受损输入从「跳过继续」变「拒绝启动」——可用性损失换来「账本缺失不能使控制权倒退」（对方架构价值句）成立。选项二（受损标记+宿主冻结）保留但复杂度高；选项三（收窄声明）不解决问题只改修辞。

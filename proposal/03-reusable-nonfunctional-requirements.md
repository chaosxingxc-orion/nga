# 可复用的非功能工程约束

版本：2026-11-02。用途：从 NGA 实验工程中提炼可用于其他工程的质量约束、测量方式和验收方法。阶段顺序见 [三阶段执行约束](02-three-stage-execution-contract.md)。本文制定工程方法，不宣称当前系统已经达到所有目标。

## 1. 应用方式

先定义并通过本批功能基线，再集中实施非功能优化。每个优化任务写清：功能版本、工作负载、问题证据、质量目标、测量方法、接受条件、回归范围、回滚方式。只报告真实测量值；未测量、未定标、测量失败与零值分别记录。

正确性、数据完整性、资源归属、基本恢复和执行终态是运行底线，不能因为归入“非功能”而延后。它们的高级保障与规模优化可后置，例如跨主机容灾、自动扩缩容、统一调度平台、极限吞吐调优。

现有明确约束包括：超过一分钟的实验脱离连接运行；常规监控约 600 秒或事件触发；过程文件三天归档；每个 milestone 刷新最新报告；当前授权最多三个子智能体并行协作。其他数值目标需要依据代表负载定标，不预设未经测量的“99.99% 可用率”“零恢复耗时”或统一利用率门槛。

### 固定负责人和持续迭代（2026-11-02 用户补充）

固定子智能体 `nonfunctional_steward` 负责持续改进，保留任务身份与交接记录，计入三个子智能体的并发额度。主线继续优先补齐功能；负责人可同时测量现状、整理故障模式，并在**已通过功能验收的组件版本**上实施非功能改进，不必等待整个 S1 结束。对未锁定的新功能，先完成该功能基线。S1 版本发布前仍做集中非功能验收。

默认节奏为每日一个小迭代、每个工程 milestone 汇总；严重故障或明确性能退化按事件调整优先级。此为工作节奏，不要求每日强行改代码，也不让模型每十分钟重新分析。每轮只选一个有证据的问题，依次记录负载与基线、目标、方案、实现、回归、独立审查及可复用经验；没有足够证据时先测量。

首轮重点是资源接续空档、启动/观测时限、CPU 结果消费延迟、重复准备与监控成本。正确性或资源归属缺陷转交功能主线。负责人不修改活动冻结包、不重复启动任务、不自行占用 NPU；需要设备的专项测试进入正常实验队列。接受后的优化只进入下一版配置/脚本；指标、人口和算法行为变化另行走科学协议修订。

固定 agent 身份不等于已部署全天候自动唤醒。当前由活跃主会话在 milestone、异常事件或日常工作开始时向该负责人派发下一轮；未部署独立日历唤醒服务时，不宣称离线期间自动开展每日模型工作。最新任务记录留在 `.local/reports/nonfunctional-steward-current.*`，必要证据留本地，验收结论与通用约束同步 Wiki/本文。

## 3. 指标定义和解释边界

### 有效利用与队列

**设备利用率**由硬件采样得出；**有效资源利用率**定义为观测窗口内有效实验工作的芯片秒除以可分配芯片秒。二者不同：等待、反复失败、重复无意义计算不能仅因硬件繁忙算成有效产出。有效工作的归类规则必须在分析前声明；短时采样无法精确覆盖所有时间时，报告采样估计与缺测范围。

“可分配”排除已声明维护或他人合法占用容量，但不可为了提高比率事后排除本系统调度导致的空闲。空闲原因至少分为无就绪任务、准入/依赖等待、数据/模型准备、资源释放、调度故障、硬件故障、CPU 消费阻塞和主动维护。

交接延迟以同一时钟源的“前驱成功释放”到“后继实际开始”为准。设备进程启动与第一条有效输出分别记录；跨主机时间差不可直接当精确调度耗时。队列深度同时列出 planned、ready、running、blocked，只有 ready 才表示可立即消费的后继储备。

### 性能与实验效率

训练吞吐报告每芯片 tokens/s、芯片数、有效 tokens 定义、reserved memory、batch、序列长度分布和测量窗口；推理报告 questions/s 时，明确是否包含多候选、多重复和预处理。模型不同、输出长度不同、温度不同或人口不同的数值不直接拼成加速比。

端到端实验耗时拆为准备、等待、NPU 执行、CPU 评分和发布。其中 CPU 评分可与其他 NPU 任务重叠，因此不能把各段简单求和充当墙钟时间。工程效率以有用实验吞吐、可解释结论产出和浪费减少共同衡量，不只优化单个 kernel。

性能优化如果改变 loss、梯度、输出、阈值或数据人口，先确定是否超出冻结数值容差；超出时属于算法/方法变更，不能作为纯性能补丁悄然替换。

### 可靠性与终态

任务成功率使用明确队列人口，attempt 成功率另列。恢复耗时从故障被确认到恢复有效进度计算，检测耗时单独记录。输出中止但容器仍在、容器退出但终态缺失、只有 heartbeat 无进度等情况保留为不确定或故障，不当成功。

本项目长实验保存固定容器名、日志、heartbeat、终态 marker、逐 item 恢复状态和精确 relaunch 命令；容器不随退出删除。实验完成以约定终态 marker 为依据，资源可重用还须有实际占用与释放证据，不能只凭容器状态或文件名。

## 4. 测试组合

| 测试层 | 主要问题 | 示例 |
| --- | --- | --- |
| 功能合同 | 输入输出和失败语义是否正确 | 已知答案评分；非法类型拒绝；固定分母；异常输出记账 |
| 真实集成 | 各组件是否真正可连接 | 实际计划入口 → 资源申请 → 推理 → 终态 → CPU 报告 → 比较 |
| 恢复与故障 | 故障后是否保留身份和数据 | 断连、缺文件、终态缺失、重复输出、资源占用冲突 |
| 代表负载 | 非功能指标在指定负载下如何 | 完整任务人口、实际序列分布、并发队列、长期运行 |
| 回归与独立复算 | 优化是否破坏已接受行为 | 同人口输出比较、指标重建、必要数值容差与重复性检验 |

测试应针对实际风险与可观察行为，避免只镜像实现或堆积数量。对生产路径使用伪造能力标志或全 mock 得到的通过，只证明 fixture 行为，不能证明真实系统具备该能力。

### 配置与脚本的变更边界

固定脚本和版本化配置是可维护基座的交付形式。新增同类实验只改配置，并生成可审阅的执行计划；不以每次新写启动程序作为正常工作流。配置格式变更必须说明兼容范围，未知类型/版本明确拒绝。新功能修改脚本、测试后发新版本；非功能优化固定代表负载单独比较；运行中的冻结脚本和配置不随主仓库升级。统计每批实验所需手工代码改动与临时操作，可发现尚未被基座吸收的重复工作。

## 5. 异步执行和监控的通用模式

执行队列、CPU 消费队列和报告发布分开。依赖以版本化产物和终态传递，单个慢分析不会阻塞无关实验；同一产物只允许明确的有效写入者。CPU 可以并行分析不同实验，涉及同一输出或资源事务的写操作保持有序。

监控使用三级结构：脚本读取日志/heartbeat/marker，形成有界 digest；分析者仅在标记异常时读取指向的片段；编排者读取摘要和诊断再判断。异常包含失败、停滞以及可疑成功，如全 0/全 1、所有单元指标相同、分母低于约定下限。

常规采用事件或约 600 秒轮询。提高采样频率需要明确故障诊断目的，限时结束后恢复常规频率。持续运行的低成本脚本可以收集统计，但不能让高频模型调用成为默认监控机制。

## 6. 可迁移的验收记录模板

每项非功能改进用以下字段形成一条记录，可直接用于其他工程：

- **功能基线：** 版本、关键行为、已通过测试和已知限制。
- **问题与负载：** 实测症状、代表输入、硬件/依赖、观测窗口。
- **质量目标：** 维度、指标公式、分母、预先确定的阈值；未定标则明确先测量。
- **改动：** 涉及组件、是否改变数据/算法/接口、回滚方式。
- **证据：** 改动前后同负载测量、异常/缺测、功能与数值回归。
- **结论：** 通过、未通过或仅限某范围通过；不能外推的环境和剩余问题。

对本项目，优先把已验证的断连存活、逐 item 恢复、CPU/NPU 异步消费、资源交接、低频监控和指标复算整理成这类记录。尚未实现的全面容灾、自动扩容或极限性能不写成既有能力。

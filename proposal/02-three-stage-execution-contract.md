# 三阶段执行约束：先锁定功能基线，再集中优化非功能特性

版本：2026-11-02。依据：用户当日明确的工程约束与业务三阶段。本文是当前**工作范围、优先级和阶段交付**的执行依据，不是实验预注册，也不替代各实验的冻结指标、数据划分、阈值、启动条件和审查要求。

历史研究路线见 [研究提案](00-research-proposal.md) 与 [四方向工作计划](01-work-plan-four-directions.md)。其中 R0–R8、G1/G2/G3 保留原科学含义；本文使用 S1/S2/S3 表示交付阶段，不宣称二者一一对应。旧方案中的长期模型规模不扩大当前实验范围；当前执行范围仍为 Qwen3.5 小于 10B 的模型与已准入参考模型。

最新实验事实以 [GitHub Wiki 当前结论](https://github.com/chaosxingxc-orion/nga/wiki/Current-Conclusions) 为入口，参考 TEST 数值见 [参考基线](../experiments/REFERENCE-BASELINE-LATEST.md)。本文不复制滚动状态，以免产生第二套事实权威。

## 1. 工程开发顺序

功能性开发回答“系统是否完成了约定任务、是否得到可解释且正确的输出”。非功能性开发回答“在明确负载和故障条件下，它能持续多快、多稳、以多少成本完成”。两类工作分别建任务、验收和记录，不能用其中一类的完成替代另一类。

开发按以下顺序推进：

1. 明确本批功能范围、输入输出、失败行为、数据和指标协议。
2. 完成最小真实闭环，并用测试锁定功能基线：真实格式输入 → 执行 → 终态 → 评分 → 比较 → 可追溯报告。
3. 在已锁定功能上集中优化可用性、可靠性、稳定性、性能、可维护性等非功能特性。每次优化重新验证受影响的功能基线。
4. 达到本阶段预先声明的非功能验收条件后形成可复用版本。新功能进入下一版本，不持续改变已冻结实验包。

“功能先行”不意味着把正确性、资源安全或已承诺的基本执行能力留到以后。错误分母、标签泄漏、无法消费真实计划、丢失输出、重复占卡、错误接续、断线导致长实验中断，都会使功能闭环不成立，必须先修复。高级容灾、通用框架重构、展示完善、尚无证据必要的极致性能优化，可以排在功能完整之后。

一次功能验收至少包含真实格式的集成路径与关键失败路径。测试数量仅是覆盖证据，不能以“数百项测试通过”代替真实入口可调用、生产配置可消费、结果可独立复算。

### 脚本化锁定与配置化启动

工程基座必须作为版本化脚本交付。常规实验通过配置触发固定入口，覆盖校验、准备、启动、依赖接续、评分和状态查询；不能每次复制临时 Python 或 shell 程序来拼装同一种实验。已有脚本优先复用，统一入口不能绕过既有资源和科学准入检查。

实验配置声明模型/任务版本、split、协议、种子/配方、资源、输出目录、依赖及必要审批证据；配置格式也须版本化并校验。完成准备后生成精确计划和输入/代码指纹，运行时使用冻结版本。普通实验只改配置；新增任务类型或配置无法表达的功能，才修改 adapter 或脚本、补测试并发布新基座版本。性能优化另开迭代，不混入日常启动。

验收必须证明：同类新实验无需改代码即可从配置走通；缺失字段、错版本、错误身份和重复启动有明确行为；可输出实际执行计划和状态；必要的恢复能复用同一配置与产物。分层实现可先接通一个真实任务，再扩展任务类型，但未支持的入口应明确拒绝，不能称全流程配置化已经完成。

## 2. 阶段 S1：锁定工程基座

**问题：在当前系统环境下，已有 Jev 类任务、开源模型及学习/优化实现，到底能够完成什么，如何统一执行并忠实测量？**

### 输入与范围

- 已有公开任务、已下载数据与开源基座模型；先逐项确认来源、版本、许可适用范围、split、样本/问题身份及原生评分协议。
- 当前 NPU、镜像、算子、tokenizer、harness 与执行队列。推理、训练、重复性诊断均是实验，不把“启动训练”当作阶段起点。
- 已授权的数据覆盖扩展继续做准入与排序；新增来源名单不算完成的新基线，不以某批来源数冒充数据集数。
- 开源学习和优化方法先用于检验训练、恢复、评估、比较的工程闭环。此处不提前开展依赖业务轨迹的系统级学习研究。

### 功能交付与锁定测试

| 功能 | 交付物 | 必须证明的行为 |
| --- | --- | --- |
| 任务与模型注册 | 有版本的数据/模型清单及 adapter | 真实样本可解析；身份和类型不丢失；不支持的形式明确拒绝 |
| 评测协议 | split、阈值拟合集、分母、指标公式、异常输出处理的冻结合同 | 手算样例与实现一致；不同统计口径分开；TEST 不参与调参 |
| 直接驱动推理 | 模型 × 任务矩阵及可恢复执行结果 | 完整预期问题集合被覆盖；缺失、重复、无效输出不能静默删除 |
| 学习/优化基本闭环 | 开源方法的训练、保存、恢复与评估入口 | 实际模型/配置能执行；恢复身份正确；产物可进入同协议比较 |
| 自动执行与交接 | 明确依赖、资源归属、终态与后继消费 | 成功可接续；失败/不确定不会被当成功；同一卡不重复分配 |
| CPU 评分与报告 | 可独立重建的逐问题结果及比较报告 | 评分不依赖人工读原始日志；主运行与辅助重复不混入同一候选均值 |
| 结果发布 | 最新 Wiki 结论、参考 TEST 入口和证据指针 | DEV/TEST、参考/自有模型、工程验证/科学接受清晰区分 |

不同参考文献的 hard/expected accuracy、温度、mask、校准和分母口径分别列出；无法对齐的结果明确标记不可直接比较。不跨任务平均成一个未经定义的“总能力分”。一致性采用预注册的 decision-level paired protocol，不能用 aggregate accuracy 替代。

### 矩阵与完成条件

以明确的模型集合 N 和任务集合 M 建立笛卡尔积清单。每格至少记录模型版本、任务/split、协议版本、状态、分母、数值与证据；状态区分已完成、待执行、阻塞和不适用。不适用需要说明架构或任务接口限制，不能为了矩阵填满伪造可比性。历史固定 38 个 model × dataset units 的参考面板仍保留原范围，不能称为完整 NxM，也不能当作 38 个数据集。

S1 验收要求：

1. 本次版本承诺的功能已全部通过真实集成与关键失败路径测试，剩余外部阻塞和不适用项有明确边界。未完成范围不能标为已测。
2. 本次冻结矩阵的可执行单元已得到所声明 split 的结果；有 TEST 的公开基线以 TEST 为主要对外指标。没有可用 TEST 的面板必须说明替代协议及证据限制。
3. 已锁定评测/统计代码、数据身份、模型身份、运行环境和结果复算入口。原生口径与本地协议分列。
4. 基础学习/优化闭环可运行，结果能被同协议消费；工程可运行不等于已获得显著收益或正式科学资格。
5. 完成功能锁定后的必要非功能集中验收，形成可复用工程版本及已知限制。验收阈值先声明，未定标项不能填写“已达标”。

新增覆盖按增量版本进入后续矩阵，不追改已发布人口或指标。本阶段可以准备 S2 的问题清单，但 S1 尚未接受的工程版本不能作为已稳定基座对外宣称。

## 3. 阶段 S2：把 System1 业务目标转化为任务、数据与评测

**问题：在 System1 + System2 架构中，System1 应承担哪些决策，现有任务漏掉了什么，如何让这些要求成为可测量的问题？**

输入是已接受的 S1 版本、公开任务覆盖与缺口、架构文档中的职责假设。此阶段仍是研究与离线任务构造，不等于真实生产业务部署。

### 交付物

1. **业务目标映射。** 将每项要求拆为输入、问题、level 定义与类型、candidate set、readout、unknown/abstain、升级 System2 的条件及错误成本。哪些由现有任务承载、哪些缺失，逐项映射；尚未经验证的架构设想标为假设。
2. **缺口数据集。** 固定来源、标注/生成规则、裁决流程、划分、版本、泄漏审计与人口。每项措施指向 defect registry 行；先说明无约束最优解，每个不变性目标都配区分性对照。
3. **新评测方法。** 在运行前固定公式、分母、阈值、等价类、异常/拒答处理和验收条件；测试样例既能发现目标错误，也能拒绝常数模型、位置捷径、忽略输入等退化解。
4. **新任务直接驱动基线。** 在冻结业务任务上汇报基础模型与必要退化/参考基线；收益须针对对应要求与同一问题人口，不以训练 reward 或单一总准确率替代。
5. **稳定轨迹与采集合同。** 定义输入版本、模型/策略版本、决策、工具/环境反馈、System2 接管、终态、错误标签和时序关联；约定缺失/重复处理、数据使用边界与回放方式。采集能力本身也要通过真实路径测试。

S2 验收要求：目标到任务的映射可审查；数据与评测冻结并可复算；新任务基线已报告；轨迹具有足够质量、覆盖和版本稳定性支撑拟议学习方法。样本量、覆盖率、回放成功率等具体门槛在任务定义时预先设定，本文不虚构统一数值。

S2 可以复用成熟开源方法做必要对照；依赖稳定系统轨迹的系统级训练研究仍由 S3 承担。业务偏好、错误代价或升级规则出现无法由证据确定的取舍时，向用户提交具体案例和备选方案。

## 4. 阶段 S3：探索系统级学习方法

**问题：在稳定任务与系统反馈上，哪些学习机制能提高 System1 及其与 System2 协作的效果？**

输入是 S2 固定的目标、数据、评测、直接驱动基线和可验证轨迹。没有这些输入，不因“已经能跑 RL”就提前进入正式系统级训练。

交付包括系统级训练方案、公开可复现方法对照、强化学习或其他候选方法、消融、异常与退化行为分析，以及同协议收益/负结果。奖励、数据采样、策略更新、System2 接管和评测之间的关系须明确；检查 reward hacking、轨迹污染和工具/环境泄漏。

S3 验收以预先约定业务任务上的真实效果、风险和资源代价为依据。使用相同冻结测试人口与统计方法，报告重复性和不确定性；训练 reward 上升不单独构成业务收益，系统收益也不能全归因于 System1 参数变化。正式候选 TEST 仍在选择、校准和候选冻结之后执行。

## 5. 跨阶段运行方式与优先级

NPU 持续消费已准入、有价值、可执行的队列；CPU 并行完成评分、错误分析、方法比较、数据准入和下一批任务准备。一个实验等待自身必需的依赖，不应让其他独立实验等待整批人工分析。可按证据调整优先级或安全中断，但不得破坏冻结实验身份。

| 优先级 | 触发条件 | 处理 |
| --- | --- | --- |
| P0 | 错误结果、数据损坏/泄漏、资源冲突、真实入口无法执行、当前实验无法正确完成 | 先修复受影响链路；其他已就绪有效实验继续 |
| P1 | 阶段内缺失功能、真实集成未贯通、协议/评分/报告无法闭环 | 补齐并锁定测试；这是当前开发主线 |
| P2 | 功能已锁定后的可用性、可靠性、稳定性、吞吐、成本与维护优化 | 集中开展有负载和指标的非功能迭代，并回归功能 |
| 后续阶段 | 业务缺口任务的正式实施、依赖轨迹的系统级学习 | 按 S1 → S2 → S3 依赖推进；允许独立文献与问题清单准备 |

NPU 满载的目标是持续有效产出。不能用重复无意义实验、错误数据任务或越过启动条件制造占用率。空闲要记录具体原因，并优先准备可执行后继；可用容量不足或依赖未就绪时如实报告。

常规监控采用终态/异常事件，或约 600 秒轮询；CPU 评分与比较服务独立运行。子智能体在已授权并发范围内承担独立任务，主会话只接收摘要、证据和需要判断的问题。细则见 [可复用非功能约束](03-reusable-nonfunctional-requirements.md)。

## 6. 当前工作的归属与重新排序

以下是工作归属，不替代 Wiki 的实时完成状态：

| 当前工作 | 阶段/性质 | 优先处理方式 |
| --- | --- | --- |
| 参考 TEST 矩阵、BEV 等已有公开任务适配与直接驱动 | S1 功能与结果覆盖 | 保持准入、推理、评分、发布闭环；TRAIN-derived DEV 只称 DEV |
| 0.8B/2B/9B 基础训练、推理、开源方法接入 | S1 学习工程功能 | 检验实际产物可消费、结果可复算；不提前宣称业务收益 |
| 角色绑定、真实计划解析、资源交接、评分/资格消费者 | S1 正确性或功能阻塞 | 先修真实失败路径，再由对应测试锁定 |
| 吞吐精调、通用重构、监控展示增强 | S1 非功能优化 | 必要底线之外，集中排在本批功能锁定之后 |

| 利用稳定系统轨迹的 RL/联合优化 | S3 | 等待 S2 轨迹与评测条件，不抢占 S1 主线 |

当前立即执行的是：完成已准备的公开任务与模型后继；贯通真实执行与评分；合并已验证功能改动；补齐 S1 功能验收清单。必要的正式实验资格工作保留，但不能把通用框架继续扩展作为所有参考推理的前置条件，也不能倒签已有实验资格。

## 7. 决策与报告维护

当前三阶段顺序、功能优先和异步运行已经由用户决定，执行中无需重复请求批准。实现细节、故障修复和既有范围内的排队由工程方处理。需要用户取舍的事项主要在 S2：优先业务能力、错误成本、System1/System2 职责边界；届时带具体任务例子与证据提交。实验方法或科学范围的实质变更按适用预注册前瞻修订，不因结果好坏修改门槛。

每个 milestone 更新同一份最新报告与 GitHub Wiki 结论，保留历史读数和日期明确的纠正说明；远程只维护最新结论、规范和必要参考入口。过程文件留本地/CephFS，超过三天按归档规则处理，保护活跃执行输入、冻结合同和当前权威报告。功能版本、非功能测量和实验科学结论分别标注验收范围。

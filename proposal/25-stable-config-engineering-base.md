# Stable configuration-driven engineering base

Status: engineering requirement and partially implemented migration, 2026-11-03. The native single-card configuration, runtime and lifecycle components passed the v3 component review. The v4 configured 9B long-DEV run subsequently passed exact dispatch review and actual numerical/lifecycle verification. The complete public-panel v6 adapter passed exact review and started the 9B fixed-base panel. Actual 0.8B long-DEV execution also demonstrated second-model reuse with unchanged executor/module hashes. This document records the owner's requirement that experiment changes enter through configuration and the core follows dependency inversion. It does not amend frozen metrics, numerical protocols, or running experiments.

The stable core owns task state, dependencies, lifecycle, item persistence, resume, logs, monitoring and result handoff. It depends on interfaces for data, prediction, validation, resource execution and scoring. Concrete implementations depend on those interfaces; the core must not select behavior by model names, dataset paths, chip numbers or experiment-specific branches. Configuration selects registered adapter identifiers and compatible versions. Arbitrary configuration strings are not executable code.

## Configuration boundary

A versioned experiment configuration declares these groups. This table is the target boundary across the engineering base, not a claim that one production schema already supports every group. The current narrow native schemas are `native-experiment-config-v1`, `native-capability-registry-v1` and `native-config-execution-v1`.

| Group | Configuration inputs | Core validation |
| --- | --- | --- |
| Identity | schema version, run ID, immutable configuration digest | known schema, exact types, unknown fields rejected |
| Sources | model manifest, input population and split, protocol contract | source hashes and compatible adapter versions |
| Adapters | predictor, arithmetic validator, data reader, scorer and executor registry identifiers | approved identifier/version; fixed dependency closure |
| Numerical protocol | dtype, batching, padding, length limit, readout mode, registered tolerances | protocol consistency; no retrospective changes |
| Resources | device count, allocation policy and shard assignments | resource transaction confirms ownership, release and applicable queue precedence under the allocation lock |
| Dependencies | predecessors and required terminal/artifact references | exact generation; missing or failed predecessor cannot become success |
| Outputs | output root, item storage and report destinations | isolated generation, single writer, retained failed attempts |
| Operations | attempt/resume policy, log fields, monitor interval | safe bounds; current approximately 600-second policy retained |

A new model, task, dataset, resource assignment or monitoring registration within existing capabilities changes only versioned configuration and its pinned registry/manifests. Configuration is validated before work or reservation starts; unknown identifiers, incompatible protocols and unsupported values fail explicitly. A configuration change creates a new immutable run identity or an explicitly compatible resume attempt, not an edit to a live experiment. New capabilities require an adapter or a versioned interface extension and contract tests; they do not require rewriting the generic launcher. Configuration cannot authorize numerical or scientific acceptance merely by setting a boolean.

The user's idle-device/no-ready-queue condition governs opportunistic new multicard tasks. It is not a global-empty-queue prerequisite for an already authorized single-card successor. That successor must still prove its exact predecessor's release, current device ownership and applicable priority reservations under the resource transaction. Other devices' queued work must remain intact. The current v1 registry field `requires_idle_and_no_ready_queue` must not be read as evidence that the entire cluster queue is empty; actual admission is a separately bound resource policy.

## Stable interfaces and composition

The composition root validates the configuration, resolves adapter identifiers, verifies implementation/source hashes, and injects adapter objects into the core. It must verify the complete executable dependency closure before claiming devices. The current shard core already accepts `predictor(request)`, `validator(prediction, request, binding)` and `metadata()` callbacks; these are dependency seams, not authenticated production adapters. Its `run_shard` API alone does not establish the callback implementation identity, model loading, device ownership or actual arithmetic equivalence.

A production adapter should provide preparation/readiness, one-item prediction, arithmetic validation, metadata and cleanup. A resource executor supplies claim/start/terminal/release operations. A scorer consumes immutable committed records only after required lifecycle checks. Data adapters preserve registered population identity and global ordinals. Monitoring consumes declared artifact paths and schemas independently of model implementations. The composition root owns adaptation and binding; the core does not import a concrete model to decide how an experiment should execute.

Functional acceptance comes first: startup rejection must produce a log and terminal once a safe output directory and writer lock exist; exact identity and false authority scope must survive retries; committed records must preserve original ordinals; scientific acceptance remains external. Invalid output paths, existing attempts and contention cannot safely receive a new terminal at the contested location and must be reported by the host launch envelope.

Only after these interfaces and behaviors pass should throughput, batching, cache strategy or concurrent scheduling be optimized under a fixed representative load. Required numerical equivalence and unchanged metric definitions remain independent conditions. No new NPU execution or multi-card launch is authorized by this document.

## Acceptance and change discipline

1. For an existing capability, add a second model/task configuration and demonstrate the same launcher and adapter source hashes. Validate configuration changes, input order, source identities and output isolation before reservation. A new capability instead supplies an explicit adapter/interface version and compatibility tests.
2. Lock functional behavior first: strict validation, deterministic readout/scoring contracts, detached retained execution, durable logs and terminal markers, exact claim/release, item-level resume and asynchronous CPU result handoff. Successful startup alone is not acceptance.
3. Optimize nonfunctional behavior against that baseline: device utilization and queue handoff delay, per-chip throughput with chip count and reserved memory, restart recovery, monitoring cost and failure visibility. Ordinary monitoring remains script driven, reading logs as well as heartbeats and terminal/report artifacts at approximately 600-second intervals or explicit events.
4. Preserve the registered numerical protocol, population, split, metric definitions and thresholds. A speed-only change must pass the applicable numerical-equivalence checks. A changed scientific protocol needs a prospective amendment; an old result is never silently relabeled.
5. Promote a reviewed configuration/adapter version prospectively. Keep active runs and their executable dependency closures frozen. Record reproducible commands and immutable evidence; retain failed attempts for diagnosis. Latest conclusions may summarize these checks, but process logs remain local/Ceph evidence.

NPU queue execution and CPU review/analysis must remain asynchronous. A completed result can await independent acceptance while the next already admitted experiment runs; an analysis task must not hold a released device. Only a concrete dependency, failed admission or explicit experimental gate should block its successor.

## Queue depth and explicit dependencies

Owner clarification, 2026-11-03: prepare multiple useful exploration tasks concurrently and keep prospective work for every NPU. Express dependencies as a versioned directed acyclic graph, rather than preparing only one successor after a device becomes idle. Report executable ready depth separately from planned and blocked reserves; a long list of templates is not available work. Prefer unfinished registered experiments and DEV-only engineering explorations with explicit hypotheses and fixed metrics; repeated completed runs need a distinct experimental purpose.

Dependencies distinguish resource release, required artifacts, numerical validation and scientific admission. CPU analysis blocks only descendants that actually require its result. A blocked task must not prevent unrelated admitted work from using the same lane, subject to existing reservations and priority. A failed experiment may release its device without satisfying its scientific descendants. Configuration determines priorities, eligible resources and edges; the resource adapter still checks current ownership under its lock at dispatch. Preserve running configurations and require prospective admission for new tasks.

The committed `async_experiment_queue.py` v1 supports per-chip FIFO and explicitly rejects dependencies. It is not a deployed DAG scheduler. The new DAG capability needs functional tests for cycles, missing dependencies, independent progress, failure propagation and uncertain launch recovery before activation. Numerical acceptance, final TEST authorization and actual designated-model review remain separate conditions. Routine graph advancement and monitoring belong to scripts and events/approximately 600-second polling, not agent polling.

## Accepted DAG composition boundary

The native composition in `tools/experiment_dag_native.py` and `experiment_dag_native_service.py` supports existing guarded long-DEV and complete-panel hosts. All 46 functional tests and five independent CPU probe groups pass. Observation errors retain uncertain ownership; explicit same-config restart preserves the intent journal; proven resource release is independent of missing or failed computation results. Existing asynchronous CPU handoff is retained. See `configs/experiments/DAG-NATIVE.md` for exact configuration and activation rules.

Acceptance currently covers the components and a plan-only example containing two external tasks. It does not activate dispatch or make the broader exploration graph executable. Upcoming shard/predictor and named-forward capabilities still require their own frozen source packages and checks. The graph records ready work separately from blocked reserves, keeps completed work terminal, and binds resource edges to the actual chip predecessor. Working-tree sources under parallel development must not be evidence pins in a frozen queue; use immutable snapshots of the already accepted bytes.

Actual configuration-only reuse is demonstrated for Qwen3.5-0.8B using the accepted 9B long-DEV executor and adapters unchanged. Nine actual forwards at three long input lengths passed independent full-logit and arithmetic equality; this is engineering evidence under that fixed load, not a general model-quality, performance or TEST-improvement claim.


## Unified Docker release requirement (2026-11-05)

The owner requires one stable, packaged engineering base capable of executing different experiments. Existing configuration components and per-run source bundles are migration inputs; they do not yet constitute this release. The deliverable is one versioned Docker image per release, identified by immutable image digest, with a reproducible Dockerfile, dependency lock/inventory, installed execution adapters, a configuration schema and a single documented entrypoint. Multiple containers created from the same image execute independent NPU or CPU tasks. A single image does not mean one long-lived container or serialized scoring.

Model weights, datasets, immutable experiment configuration and durable output remain mounted external data. Runtime Python packages, adapter implementations and executable dependencies belong in the image; no per-experiment pip installation or mutable host virtualenv supplies the runtime. The host retains the NPU driver, container runtime, physical-device allocation lock and a thin, versioned launch/reconciliation interface. CANN environment variables required by operator compilation must survive safe Python startup. If incompatible libraries require isolated environments inside the image, those environments are installed and pinned at build time and selected by registered configuration profiles, never synthesized during a run.

| Release capability | Acceptance evidence |
| --- | --- |
| Fixed-base inference across supported Qwen3.5 sizes and registered datasets | At least two existing model/task configurations use the identical image and entrypoint; actual frozen-input output equivalence against accepted evidence, with no TEST-driven reselection. |
| LoRA training and checkpoint resume | Existing approved training recipe runs through configuration; item/step recovery, optimizer/scheduler state and applicable numerical agreement are verified. A fixture alone does not establish production training support. |
| CPU validation and scoring | Same image runs without device mounts; frozen saved-readout metrics reproduce accepted arithmetic, bounded parallel workers, NPU release independent of analysis. |
| Resource profiles | Configuration selects one, two or four cards as applicable; 27B starts with its authorized four-card profile. Atomic group ownership and release are tested. Budget authorization is not successful runtime evidence. |
| Durable execution | Retained detached containers, Ceph logs, heartbeat, canonical terminal, exact relaunch command and resumable items survive disconnect and tested failure paths. |
| Declarative extension | A supported new model/dataset/seed changes configuration only. A new capability extends a versioned adapter and contract tests, then ships a new image release. Arbitrary shell commands in config are not an adapter registry. |
| Reproducibility and failure visibility | Image/source/dependency/config digests accompany every run. Wrong schemas, unavailable adapters, inconsistent sources and incompatible driver/runtime profiles fail before device ownership where possible. |

Implementation order is functional baseline first: inventory verified existing paths, package dependencies and adapters, exercise actual host/container entrypoints, run functional regression and independent adversarial review, then promote an immutable release. Package preparation and CPU regression proceed asynchronously with already accepted experiments; migration is not a new gate on their launch. Existing frozen runs and failed evidence remain unchanged. Only release generations that pass their applicable tests become the default for new experiments.

After functionality is locked, optimize queue handoff, batching and CPU parallel scoring under unchanged numerical contracts. Report ready queue depth, device idle causes, per-chip throughput, total card-seconds, peak reserved memory, recovery behavior, scoring latency and monitoring cost. Event-driven scripts with approximately 600-second fallback read logs as well as heartbeat/terminal files. Release claims must distinguish a built image, CPU-tested image, NPU-validated capabilities and the final promoted base; none implies the others.

# Frozen DEV engineering smoke (before NPU execution)

Objective: validate task-length scoring on the released post-trained Qwen/Qwen3.8-27B text path, not estimate model quality. Image `sha256:8190b3ec51929baca2388452039ccf05d681c01b7c91cc55dd1e7ac5570a76b7`, checkpoint revision `1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0`, float32, SDPA, HF32 disabled, one candidate per forward, four balanced logical NPUs, no CPU/disk offload. This differs from the existing scorer's typical bf16 runs and is not a cross-family scaling comparison. Two-card routing is parameterized but has no admission or feasibility evidence.

Workload `WORKLOAD.json` was frozen by tokenizing all four SHA-256-verified DEV masks, selecting row zero from each file and the longest full-input prompt plus candidate by actual token count (lexicographically greatest key/index breaks equal length); the longest is decision-v7/dev row 56, 1,033 tokens. The five items are independently run in full, blank-input, and question-only modes. Variants here need not pair with selected originals: no paired consistency or discrimination result can be claimed from this smoke. No metric-based selection, public TEST read, or chat template. Hard sequence limit is 2,048 and checked against model context; overlong input errors, never truncates. The frozen lengths of full-input rows are checked at runtime.

Method: `r0-prompt-v2` record_name prompt; tokenize prefix and each candidate separately without special tokens, concatenate. For candidate of n tokens request n+1 final logits, verify exact shape, and sum float32 log-softmax at rows 0..n-1 for the corresponding candidate IDs. This is the existing `HFScorer` formula, including multi-token candidates, not the accepted synthetic forward's last-token-only route. Records preserve original candidate order and gold identity; every full candidate gets a raw sum. Each completed item/mode is atomically persisted and checked on resume. A partially completed item is recomputed. Per-candidate elapsed time is saved in item records and peak reserved memory appears in the heartbeat; item card-seconds are wall seconds times chip count. These are inference figures, not training throughput.

Before any NPU launch: owner schedules a truly free whole group without preemption, records experiment purpose/hypothesis/setup in wiki, reviews the launcher and protocol, confirms image/driver/assets and frozen files on the target host, and captures relevant claim/release instructions. No historical job is restarted. Launcher uses the accepted group helper's locked atomic claim and physical conflict checks, then checks conflicts again before `docker run -d`; it retains the claim on error for explicit reconciliation. The claim is not a replacement for owner scheduling or a monitoring controller. The output directory must not be concurrently used by another run.

Expected checks: source/loader accounting passes; physical mapping and placement use the selected devices; HF32 off; no offload; all finite scores, valid lengths, and peak reserved memory below 56 GiB per chip. Check actual 1,033-token case, multi-token candidate values against independently evaluated reference formula using the same model/logits, and inspect CPU/NPU memory and timing. Verify interrupted-item retry and completed-item skip on real outputs. The `EXIT.json` of each attempt is the completion truth; container exit alone is not a substitute. If the process is killed without the shell trap, the missing marker is an incomplete/unknown run. Release the atomic claim only after retained-container identity, termination and absence of live device conflict are confirmed. The smoke is not a full DEV reference, paired report, training run, nor permission to use TEST. Full DEV, paired reporting, baselines, protocol acceptance and public TEST prerequisites remain separate work.


## Bounded review amendment, before launch
The frozen five items, three modes and all 723 candidate forwards remain unchanged. The first attempt is four cards. Before execution select the first multi-token candidate in the longest full item: decision-v7/dev row 56, candidate index 0, three tokens. Store its final four FP32 vocabulary rows and candidate IDs, checksum, and NPU score. After group release, CPU log-softmax reconstructs its score; pass uses abs tolerance 0.0001 or relative tolerance 0.00001 and records actual absolute/relative differences. This tests reductions on identical NPU-produced logits, not an independent model forward. Differences are not yet measured.

Runtime receipt records observed dtype counts and HF32 flags. Each item records candidate durations, cumulative per-chip allocated/reserved peaks and process peak CPU RSS; attempts record item starts, commits, computed and skipped counts. Interrupted uncommitted items restart at the first candidate. Real NPU execution, actual timing/memory, reference differences, interrupted retry and resume/skip remain untested.

The detached controller waits at most 600 seconds for the group to become free after main drains selected lanes. While the container runs it uses docker wait with 600-second observer heartbeats, with no model-progress timeout or stop. On terminal exit it requires a current authoritative host ownership probe, then calls the existing adapter with exact claim and retained container identity. Nonzero exit remains failed while the group can be released. Missing EXIT stays unknown. Any uncertainty holds the claim. The controller is not to be started until main integrates queue coordination and supplies a host ownership probe that returns the specified JSON on certain absence of unmanaged owners.
